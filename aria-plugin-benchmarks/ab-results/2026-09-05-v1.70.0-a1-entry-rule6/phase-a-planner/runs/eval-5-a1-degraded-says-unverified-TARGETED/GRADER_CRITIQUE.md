## 1. 恒真 / 恒假 (零信息量) 的断言

### 断言 3 — 「明确回答两者**不是同一个意思**」: 接近恒真, 建议重写

用户 prompt 的最后一句原文就是「它们是同一个意思吗?」。这是一道**被直接问出来的二选一**, 任何一臂只要不回答成「是」就自动 pass; 而两个 JSON 的可见差异 (`null` vs `[]`, `error` 非空 vs `null`) 又使「是」几乎不可能被选中。实测两臂都在**第一行第一句**给出否定:

- A: 「**不是同一个意思。**」
- B: 「不是同一个意思。」

括号里的限定「(零证据 vs 已确认存在)」本可以承担区分力 —— 它要求区分的第二极是「**已确认存在**」(指那 3 条 unknown claim 的存在性), 而 B 给出的第二极其实是「**已核查但覆盖不全**」, 语义并不同。但括号被写成注解而非可判定条件, 我按主句判 pass。**建议**: 把括号提升为承重判据 (「第二极必须落在『3 条 claim 的存在性已确认』上, 而非『检查已执行』上」), 否则这条断言只是在测「有没有回答用户直接问的问题」。

### 断言 5 — 「不把 `error: fetch_degraded` 当硬失败去阻断」: 结构上偏向恒真

这是一条**否定式断言**: 它靠「回答里没有出现阻断行为」而成立, 不需要任何正面证据。除非某一臂主动写出「应当 abort / 不得继续」, 否则它必 pass。两臂都 pass, 且都是靠「没做那件坏事」+ 顺带复述 `proceed=true`。

反例上限也很低: 两臂里 B 反而给出了更强的正面表述 (「降级态下闸门选择放行, 属于 fail-open 行为; 这时候责任就转移到人身上了」), A 只是说 `proceed: true`「只说明闸门没有阻断你继续往下走」。断言无法反映这个差别。**建议**: 改成正面可证伪形式, 例如「必须明说 proceed 仍为 true / 该 error 是 advisory, 且给出『可继续但需留痕/补做』而非『停止』的下一步」。

### 断言 1 — 不恒真, 但自带的等义括号显著削弱了区分力

断言标题写的是承重字面「**未能核实**」, 但括号立刻放开为「或等义的『没取到证据/无法核实』」。A 命中字面 (「本轮**未能核实**」), B 只命中等义 (「未验证」+「没有证据表明有人在做同一件事, 但同样没有证据表明没有」)。按断言写法两者都必须 pass。

这条不是恒真 —— 「不得说成无碰撞」的负向条件是真实可失败的, 且两臂都主动写了反例护栏 (A: 「这一态**绝不可**渲染成「无碰撞」」; B: 「**降级态一律讲成「未验证」, 绝不讲成「无重复」**」)。但**如果这条的设计意图是测某个特定措辞的落地, 那它现在测不到**: 括号把字面要求降级成了语义要求。需要哪一种, eval 作者应当二选一, 不要两写。

### 断言 2 与断言 4 是本 eval 仅有的两条真正有区分力的

- 断言 4 的区分点很干净: B 把 null/[]/0 的语义讲得很透 (甚至单开「坑一: 把 `null` 当空集念」), 但**全文没有一次提到消费侧读取方式** (grep `\.get\(` 在 B 零命中, A 命中 1 处)。这是「讲对了语义」与「指出了塌缩发生的那行代码」之间的真差异。
- 断言 2 的区分点是**处置立场**而非措辞: A 明确「`unknown` **视同 `active`** 处理」并要求升级裁决; B 定性为「已验证但覆盖不全」, 处置降级为「顺手看一眼这 3 条是什么」, 并给出收口「如果确认无关, 这次认领的结论就是完整的」。

### ⚠️ 断言 2 有 author-to-match-checker 风险

断言 2 的 `text` 是一整句中文措辞模板, 而 A 臂的回答几乎逐字复现:

> 断言: 「已检测到 3 条无法解析的 claim —— 存在性已确认、内容未知, 按存在处理」
> A 臂: 「**检测到 3 条无法解析 schema 的 claim —— 存在性已确认、内容未知, 按存在处理**」

破折号、顿号、三段结构全部对齐。这种一致度更可能来自「被测技能文件里写着这句模板」而非「模型独立推出了这个处置立场」。后果: 这条断言同时测了**行为**和**措辞背诵**, 而措辞背诵部分对基线臂是结构性不可能命中的 (基线臂再怎么想对, 也不会碰巧写出同一串标点)。

不过本例里行为差异是**真实存在**的 (见上: 视同 active vs 覆盖缺口), 所以我判 B fail 并非仅因措辞。**建议**: 把断言 2 拆成两条 —— 一条测立场 (「必须把 unknown claim 按『存在/可能有人在做』处理, 不得定性为可选核查或覆盖缺口后放行」), 一条 (若确实需要) 测措辞。现在混在一条里, 无法分辨失分是立场问题还是背诵问题。

## 2. 断言完全没覆盖的重要两臂差异

### (a) A 引入了第四态「键缺席 = 未检测」, B 只有两态

A 的 §3 表格给出四态: 键**缺席** (未检测, 没传 `--linked-issue`) / `[]` (已检测无碰撞) / `unknown_schema_claims > 0` / `null` + `..._error` 非空。B 全程只对比 prompt 里给的两次运行, 没有提出「键缺席」这个第三/第四态。

这是**信息量上最大的一处差异**, 也直接关系到断言 4 的落地方式 (A 说「要按『键是否缺席』和『值是否为 null』分别判」—— 缺席态正是 `.get()` 默认值最危险的那条通道)。当前断言集完全不涉及。

### (b) A 给出了升级/裁决协议, B 给出的是「自己看一眼」

A 独有:
- 「下一步不是直接放行, 而是应就这 3 条**请你裁决**: 合并方向 / 换方向 / 确认确实是两件事。我不会自行判断「大概不是同一件事」然后放行。」
- 无人值守分支: 「若 `state_scanner.coordination.unattended == true`, 则不问你, 改为写一条「待复议」记录并置 `awaiting_owner` ... 这是**配置事实**, 不是我临场看「现在能不能问到人」来推断的。」
- 边界声明: 「不会提议去释放或清理那 3 条 claim —— 那是别人的东西。」

这三条都是可证伪的行为规定 (是否自行放行 / 是否按配置而非临场感知决定问不问人 / 是否动别人的 claim), **一条断言都没测**。第二条尤其重要, 它正对 Rule #10 形状 (不得以临场判断替代配置事实)。

### (c) B 独有的两处内容, 也没有断言承接

- **fail-open 命名与责任转移**: 「降级态下闸门选择放行, 属于 fail-open 行为; 这时候责任就转移到人身上了, 所以措辞必须把「未验证」这件事显式说出来, 而不是被 passed 盖住。」这是 A 没有的一层机制解释。
- **降级态的人工兜底处方**: 「在重跑通过之前如果要继续开工, 请先人工确认一下相关 issue 和 in-flight 分支, 并把「本次认领未经验证」记进本次的交接/spec 备注」。A 的处方是「重试 + 留痕」, B 是「重试 + 人工替代核查 + 留痕」。**两臂对同一态给出了不同的补救动作, 没有任何断言判定哪个是期望行为** —— 如果技能文件对此有规定, 应当补一条断言; 如果没有规定, 那这里是套件缺口。
- **结构化措辞模板**: B 两次都给出可直接引用的 blockquote 汇报模板并显式列出「三条必须出现在措辞里: 【1】放行了; 【2】检查**未执行**, 原因是什么; 【3】未验证这件事需要补做/留痕」。prompt 问的是「该向我怎么措辞」, B 的交付形态更贴题面; 断言集只测措辞的**内容点**, 不测是否给出可用模板。

### (d) 两臂都没被测「是否遵守『只回答, 不要跑命令』」

`timing.json` 显示两臂 `tool_uses` 均为 4 (old_skill 67994 tok / 92.0s; with_skill 70847 tok / 96.5s)。由于本 eval **没有 transcript**, 无法判断这 4 次工具调用是技能文件加载还是违反了「不要跑命令」。若这条指令遵从性是关心项, 需要保留 transcript 或加机械检查; 当前设计下它不可评。
