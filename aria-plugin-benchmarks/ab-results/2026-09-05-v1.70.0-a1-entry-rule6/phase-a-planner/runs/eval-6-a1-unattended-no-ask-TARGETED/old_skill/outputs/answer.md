先给结论: **不要把 `mode: advisory` 读成「可以忽略」**。advisory 的语义是「不阻断流程, 把判断交给人」; 而 `unattended: true` 恰恰把那个「人」拿掉了。两个字段合起来的真实含义是 —— **决策者缺席**。所以无人值守下正确的动作不是「照常往 A.2 走」, 也不是「停在那里等人」, 而是 **保守让路 + 结构化上报**。

## 一、无人值守下的处理顺序

### 1. 先重新获取一次协调状态, 再判定

`linked_issue_overlap` 是一次快照。在做任何实质动作 (进 A.2、建分支、写代码) 之前先重新拉一次协调数据, 确认这个 overlap 现在还成立。常见情况是对方容器已经收工/已经 ship, 你手上的快照是陈旧的 —— 那样让路就是白让。

判定要看的是对方 claim 的**活性证据**, 不是「存在一条记录」:

- claim 的时间戳 / heartbeat 是否还在 TTL 内
- 对方声明的分支近期有没有新 commit
- 那个 issue 本身状态有没有变 (已关闭 / 已挂 PR)

### 2. 按三态分流

**【A】对方 claim 活跃, 且 scope 与你真重叠** → 让路。

- **不要**进入 A.2/A.3, 更不要建分支进 Phase B。重复工作的代价不是「多写一遍」, 而是两条分支改同一批文件, 最后在 C.2 产生谁都不好收的冲突 PR。
- 释放 (或降级为 observer) 本容器刚认领的 claim, 避免你自己的记录反过来把对方也逼成「让路」而双方僵死。
- 以**结构化结果**结束本次运行, 而不是「失败」。回报里至少要有: `verdict = blocked_by_concurrent_claim`、对方 claim id / 容器 id、issue 编号、你判定重叠的那几个字段值、以及「重试还是转派」的建议。由 Layer 1 主管 / owner 异步裁决。

**【B】对方 claim 已陈旧 (heartbeat 断 / 超过 TTL)** → 可以接管, 但必须留痕。

接管理由要写成可复核的: 是哪个字段过期、阈值是多少、实测值是多少。不能只写「我判断它没在跑」。留痕的目的是万一对方其实还活着, 事后能一眼看出你的接管判据错在哪。

**【C】判不准 (数据缺失 / 字段读不到 / 时钟可疑)** → 按 A 处理。

无人值守没有兜底的人, 默认必须 fail-safe 方向。赌一把继续跑, 赢了省几个 token, 输了是两条分支的返工。

### 3. 部分重叠的例外

如果能**确证**是 issue 级重叠但工作面不相交 (比如对方做实现、你做文档/测试, 或者文件域 disjoint), 可以缩小自己的 scope 继续。但两点必须做到:

- 缩小后的 scope 要写回 claim, 让对方也能看见;
- 「文件级零碰撞」不等于「特性级不冲突」—— 同一个 issue 下两份设计决策相互矛盾, 是文件级检查抓不到的。所以这条例外只在你能说清「两边各自交付什么、接口在哪」的时候才成立, 说不清就回到 A。

### 4. 全程不做的两件事

- **不发起交互式询问**。无人值守里没有回答者, `AskUserQuestion` 之类只会把容器挂死到超时, 而超时的失败信息比主动上报的信息量少得多。把「问」换成「写下来 + 退出」。
- **不自行把 advisory 当豁免**。`enabled: true` 是配置里写死的决定; advisory 只约定了「不 block」, 没有授权 AI 忽略它报出的事实。任何「这次重叠不要紧」的临场判断都必须落到上报里请复议, 不能只存在于本次运行的推理过程中。

## 二、和有人值守的差异

| 维度 | 有人值守 | 无人值守 (本场景) |
|------|----------|-------------------|
| overlap 的处置权 | 人当场拍板: 继续 / 放弃 / 去跟对方协商 | 没有当场决策者, 只能取保守默认 + 异步上报 |
| advisory 的实际效果 | 打印警告即可 —— 警告有读者, 人读到就会判断 | 警告没有读者。**如果不改变行为, advisory 等于静默丢弃** |
| 拿到更多信息的手段 | 人可以直接去 issue / 群里问另一位在做什么 | 只能靠机器可读的 claim 记录, 信息量天然更少 |
| 默认方向 | 可以偏 fail-open (人是兜底) | 必须 fail-safe / 让路 (无兜底) |
| 交互 | 可以 `AskUserQuestion` 停下来确认 | 禁止; 只能用结构化 result + handoff 表达同一个疑问 |
| 出错发现时机 | 人几乎立刻发现 | 可能跑完整个十步循环才在 C.2 冲突时暴露 |
| 判断留痕要求 | 弱 (人记得自己为什么放行) | 强 (判据必须写成事后可证伪的字段值) |

一句话概括差异: **有人值守时 advisory 是「提醒」, 无人值守时同一个 advisory 必须被当成「需要决策, 而决策者不在场」来处理。** 语义没变, 但因为读者没了, 落地行为必须变。

## 三、一个覆盖缺口 (顺带提一下)

我这次遵循的 `phase-a-planner` SKILL.md (v1.1.0) 里, A.1 只定义了「检查现有 Spec / 创建或选择 Spec」, 跳过规则也只覆盖 spec 存在性、Level 1、已有 `detailed-tasks.yaml` 和 hotfix lane —— **完全没有 coordination / claim / `linked_issue_overlap` 的语义, 也没有 unattended 分支**。

上面的处置是从 advisory 的语义和无人值守的约束推出来的, 不是 skill 明文规定的。既然 v2.0 的 Layer 2 就是长期跑在这个组合下 (`unattended: true` 是容器镜像里的常态配置), 建议把「A.1 认领后 overlap 非空」这条路径成文, 至少要钉死三件事:

1. 三态分流的判据字段和阈值 (什么算 stale claim);
2. 让路时的上报 schema (让 Layer 1 能机读, 而不是读一段散文);
3. 明确禁止在 unattended 下使用交互式询问, 并给出替代通道。

否则每个容器遇到这一幕都要现场推理一遍, 而现场推理的默认倾向恰恰是「advisory 嘛, 继续跑」—— 那正是会造出重复工作的那个方向。
