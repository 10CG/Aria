## 总体判断

`linked_issue_overlap` 命中 4 条 = 有 4 条 claim 记录和你一样挂在 `10CG/Aria#174` 上。但**同一个 issue 下的 claim 不等于同一份工作** —— 一个 issue 完全可以合法地拆成多条 track。所以这里真正要判的是 **scope 是否重叠**, 而不是 issue 号是否相同; issue 号相同只是把这 4 条捞出来的筛子。

- **scope 部分重叠** → 和 cA 划清边界后把你的 claim scope 收窄, 并在 claim 记录里写明与 `aaaa1111` 的分工。

## 3. `oauth2-spike-cccc3333` (cC, abandoned, 2026-09-03) —— 不阻塞, 但要读它「为什么被放弃」

abandoned 对并发没有影响, 它唯一的价值是失败信息: 一个挂在同一 issue 上的 spike 被放弃, 通常意味着有人已经踩过坑 (方案不可行 / 前置条件不具备 / 被更好的方案取代)。

别因为它是 abandoned 就跳过 —— 它是三条里成本最低、也最容易被漏掉的一条。

## 4. 空记录 (`track_id` 空 / `container` 空 / `status: "unknown"` / `linked_issue: null`) —— 脏数据, 必须 fail-closed

这条和 `unknown_schema_claims: 1` 是同一件事: gate 读到了一条不符合 schema 的 claim 记录, 字段全是空/占位, `linked_issue` 甚至是 `null`。

**关键点: 它既不能被当成「第四个 overlap」, 也不能被当成「无冲突」。** 它是不可判定的 —— 你不知道它挂的是不是 #174 (`linked_issue` 是 null, 说明它是作为未知项被一并列出, 不是被匹配上的), 也不知道它背后有没有一条真实在跑的 track。

处置分两步:

- **眼前 (fail-closed)**: 在核实之前视为「可能存在未知并发」, 不要因为字段是空的就当它不存在。核实手段是回到 claim 记录的原始存储: 哪个文件 / 哪条记录写坏了、写入时间、哪个容器写的 —— 确认它是残留空壳, 还是一条真 claim 的损坏副本。
- **长期 (开单)**: 这是 claim **写入侧**的缺陷 —— 一条 schema 不合规的记录能进到 gate 输出里, 说明写入端没有校验。而且 `unknown_schema_claims` 只是把它**计数**了; 如果没有人消费这个计数, 它等于静默, 应该有明确的阻断或告警路由。

核实结果的两个分支:

- 确认是空壳残留 → 清掉它, 并在 handoff 里记一笔。
- 确认是真 claim 的损坏副本 → 它升级成**第二个需要协调的对象**, 回到第 1 条的流程走一遍。
