## 2. 为什么是这个路径，而不是另一个候选

另一个候选是 `standards/openspec/changes/task-list-due-date-sort/proposal.md` —— 它有诱惑力，因为 `standards/` 子模块里**确实也有一个 `openspec/` 目录**，看上去"OpenSpec 的东西都放那儿"很自然。但它是错的，理由三条：

1. **归属**：`standards/` 是从 aria-standards 引入的**共享子模块**，它是所有采用 Aria 方法论的项目共用的规范仓。"给任务列表加按截止日期排序"是 todo-web **自己的产品需求**，不是对共享方法论的修改。变更该落在哪里，判据是"谁拥有这个需求"，不是"哪个目录看起来更像 OpenSpec 的家"。
2. **后果**：写进 `standards/` 会让这份 todo-web 的产品 proposal 对**每一个**采用 aria-standards 的项目可见，而在那些项目眼里它无人拥有、无人维护、也无法验收；同时提交会落进子模块自己的历史里，todo-web 主仓只留下一个 gitlink bump，Spec 与它所描述的代码变更就脱钩了。
3. **规则**：这正是 Aria **不可协商规则 #5**（"项目变更放本项目 `openspec/changes/`，不放 `standards/openspec/changes/`"）要挡的事，spec-drafter A.1.4 也在路径落点上明写了这条警告。

反过来的边界也说清楚：**只有对共享规范本身的变更**才落 standards 仓 —— 比如改十步循环的阶段定义、改 `proposal-minimal.md` 模板、加一条新的 convention。todo-web 的排序功能不属于这一类。

另外顺带排除两个次要误区：不要放 `docs/`（那是产品/架构文档，不是 OpenSpec 变更目录），也不要放 `.aria/`（那是本地配置与运行时产物 namespace）。

## 3. proposal.md 全文

````markdown
# 任务列表按截止日期排序

> **Level**: Minimal (Level 2 Spec)
> **Status**: Draft
> **Created**: 2026-09-05
> **Linked Issue**: `none`

## Why

当前任务列表只有单一的默认排序（创建顺序 / 手动顺序），用户无法快速判断"哪些任务快到期了"。有截止日期的任务被埋在列表中间，只能靠肉眼逐行扫 due date 列，临期任务因此容易被漏做 —— 这是任务工具最不该失手的场景。提供"按截止日期排序"选项，让用户用一次切换把最紧迫的任务顶到列表最前面，直接降低漏做临期任务的概率。

## What

在任务列表视图新增"按截止日期"排序选项，与现有默认排序并列、可自由切换。

- **排序控件**：列表头部提供排序选择器，至少包含"默认"与"截止日期"两项；选中截止日期时可在升序（最早到期在前）与降序之间切换。
- **空值语义**：无截止日期的任务在升序结果中统一排在所有有截止日期的任务**之后**（不得被当作"无穷早"顶到最前，也不得与"最晚到期"混淆）；降序沿用同一分组策略，保证排序是全序、结果可预期。
- **稳定性**：截止日期相同的任务保持既有默认次序，同一输入重复排序结果逐项一致，不出现顺序抖动。
- **与筛选组合**：排序作用于筛选之后的结果集，不改变结果集成员，只改变顺序。
- **偏好保持**：用户选定的排序在同一会话内的列表刷新 / 筛选切换后保持。
- **范围外（本次不做）**：不改任务数据模型（不新增字段）、不引入多列复合排序、不改分组与筛选功能本身、不做服务端排序改造。

### Key Deliverables

- 任务列表排序控件（新增排序选项 + 升/降序切换）
- 排序纯函数（输入：任务集合 + 排序键 + 方向；输出：有序任务集合；含空 due date 归位与稳定性保证）
- 列表视图接线（排序状态 → 渲染顺序，并与既有筛选正确组合）
- 会话内排序偏好保持
- 排序逻辑单元测试 + 列表交互测试
- 用户文档中列表排序选项的说明

> 具体文件路径留到 A.2 任务规划阶段按 todo-web 实际目录结构补全；本 Spec 只写到交付物层面。

## Framework Constraints

本次需求描述未给出 todo-web 的具体前端技术栈。若 todo-web 是 framework 项目（Next.js / Astro / SvelteKit / Vue / Remix 等），实施前需在本节补齐该框架的已知约定与反模式，供 post_spec / post_implementation 审计直接对照；若不是 framework 项目，本节整体删除。

待确认项（无论哪种栈都值得先答）：

- 排序状态放组件本地 state、URL query 还是全局 store（决定"刷新后是否保持"与可分享性）
- 若有 SSR：服务端首屏与客户端 hydration 的排序结果是否一致（日期解析在两端必须同结果）
- 截止日期的时区口径（按用户本地时区还是 UTC 归一），跨时区用户看到的"今天到期"必须一致

## Impact

| Type | Description |
|------|-------------|
| **Positive** | 临期任务一键可见，直接降低漏做率；排序抽为纯函数后可复用于后续其他排序键（优先级、创建时间等） |
| **Neutral** | 新增一个列表级 UI 控件；任务数据模型不变，无 API 契约变更，无数据迁移 |
| **Risk** | 空 due date 与时区口径若不明确，用户会看到"像是随机"的顺序 —— 这是本变更最可能的返工点 |
| **Risk** | 排序与既有筛选的执行顺序若接错，会得到错误的结果集（而不只是错误的顺序），需在验收中显式钉死 |
| **Risk** | 若在客户端对全量任务排序，任务量大时可能出现可感知延迟，需给出量级门槛 |

- [ ] 1000 条任务下切换排序的可交互延迟 <= 100ms（本地基准测量，非正式性能测试）
````
