# v6 预登记修订 (v6b): 不健康调用按「能否改变判定」处理 (2026-09-15, 重跑前写定)

## 为什么修订

按原预登记 (`PREREGISTRATION.md`) 跑完: A 故障矩阵 17 个用例、B 真实报错探针全部符合预期。C 真实全量两臂里, 负控臂 60 次调用有 2 次被判不健康。逐条查明: 两次的输出流都只有 init、status、1 个 rate_limit_event 与 5 次 api_retry, 没有任何消息帧, 耗时 120.4 秒与 120.2 秒 —— API 连续重试, 120 秒内没拿到回应, run_eval 超时后把它们记成「未触发」。这是真故障, 检查判得对, 不是误报; 但原预登记写的预期「两臂检查均健康」不成立。

按原设计「任一调用不健康即作废」, 这一轮会作废。本次 120 次调用里 2 次撞上重试风暴; 按这个频率 (约 1.7%), 一轮 120 次调用全部健康的概率约 13%, 多数轮次会作废, 规则不可用。原预登记的判读规则只写了「出现误报」怎么办, 没写「真故障太常见」怎么办, 所以这里另行写明修订, 并按原规则的精神把 A、B、C 全部重跑。

## 修订后的设计 (重跑前冻结)

1. 垫片另把本次调用的 `-p` 参数 (query 原文) 写进同名 `.query` 文件; 检查脚本据此把每次调用对到 run_eval 输出里的 query 上, 不依赖调用顺序。有调用对不上任何 query, 或某条 query 的日志数不等于它的 runs ⇒ void。
2. 单次调用的健康判定不变 (起止记录齐全、有判定事件、结果帧不报错、耗时小于超时阈值减 1 秒)。
3. 不健康的调用不再一律作废, 改问「它能不能改变判定」:
   - 不健康调用的真实结果未知, 按「触发」「没触发」两种可能都算。输出流里出现过 tool_use 的不健康调用, run_eval 可能已把它记成触发 (超时余量边缘那一类), 同样按两种可能算; 输出流里没出现过 tool_use 的, run_eval 只可能记成未触发。
   - 由此每条 query 的真实触发次数落在一个区间里。被评臂: 各 query 取最不利一端门仍通过 ⇒ pass; 取最有利一端门仍不通过 ⇒ fail; 其余 ⇒ void。负控臂: should-trigger 命中数 (触发率 ≥ 阈值的条数) 的上界 ≤ 5 ⇒ valid, 否则 void。
   - 检查脚本加参数 `--role evaluated|negctrl`; 退出码 0 = 判定不受不健康调用影响 (pass / fail / valid), 1 = void, 2 = 无法判定。
4. 其余不变: 垫片经 `tee` 另存 stdout、首尾写起止时间、stderr 另存; 超时余量 1 秒。
