## Significant findings (3 worth deeper memory)

### 1. Latent inline UQ constraint blocking M5 rework (T1.5)

M2-era schema declared `CONSTRAINT uq_issue_active UNIQUE (issue_id)` inline alongside the partial `uq_issue_active_partial WHERE state NOT IN (S_FAIL, S9_CLOSE)`. Author's comment claimed inline was "fallback for SQLite < 3.25" — **incorrect**: in modern SQLite both are active, inline is always-enforced.

- M3/M4 retries dodged this by mutating same row (UPDATE attempt_count++).
- M5 review-loop spec requires NEW rows per `/aria changes` / `/aria redo` / system-retry.
- Discovered during T2 smoke testing per `feedback_pre_draft_bug_hunt_discipline` (bug hunt during smoke, fix in same iteration).
- Fix: migration 005 table-rebuild (CREATE NEW / INSERT FROM OLD / DROP / RENAME / recreate indexes). SQLite doesn't support DROP CONSTRAINT directly.

**Memory worth adding**: `feedback_inline_vs_partial_unique_overlap` — pattern lesson for future schema audits.

### 2. Spec REFRAME: `retry_count` already existed (T1)

Spec proposal §SQL literal includes `ALTER TABLE ADD COLUMN retry_count INTEGER NOT NULL DEFAULT 0;`. The column already exists since v2.0 (M3 baseline, `schema.sql:108`). Re-adding would fail with SQLite "duplicate column name". M5 reuses for B Failure-analysis system-retry guard per QA-2 semantic intent.

Three-place documentation per `feedback_spec_reframe_in_session`: (a) 004 SQL header, (b) commit message, (c) tasks.md note.

### 3. Statement splitter bug (T1 bonus)

Original `schema_migrate.py::apply_migrations` used `sql_text.split(";")` to split migration SQL. Broke on CREATE TRIGGER `BEGIN ... END` bodies because inner trigger-step semicolons split the trigger in half. Replaced with `_split_sql_statements()` — BEGIN/END-aware tokenizer. Pre-M5 migrations unaffected (002/003 have no triggers).
