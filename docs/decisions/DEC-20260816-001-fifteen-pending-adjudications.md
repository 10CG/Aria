## 2. 裁定之间的三处交互 (AI 发现, 请知悉)

### 2.1 A2 + A3 同向推向 A, 而 B2 冻结 A 的审计 ⇒ A 会积累**未审的入向工作**

A2 [2] 与 A3 [1] 都把义务推给 Spec A, B2 又裁定 A「只收不审」。净效果: 前置 change ship 之前,
A 的 proposal 会**长出两块从未过审的内容** (规则 #8 同步腿 + SC-M6 整条 + 其 3 处镜像)。

⚠️ **后果**: 等定档落定、A 终于跑最后那一轮 R6 时, 被审对象与 R5 相比已实质变化 ⇒
**R6 与 R5 的条数比 R5 与 R4 更不可比**。这不改变裁定, 但意味着「余 1 轮」的信息价值低于账面 ——
若届时发现一轮不够, 需要 owner 再裁一次加轮。**此处提前留痕, 不在事后追认。**

### 2.2 C2 的 custom check 可能**就是** A1 (iii) 要找的承载者

A1 (iii) 要的是「gitlink 在 Phase C.2 被核验」这件事有人承接; C2 要建的正是一条
「主仓 gitlink 是否指向子模块 master 上已存在的 commit」的仓级 custom check。

⇒ 若 C2 先落地, A1 的「Phase C 交接材料」可以直接指向它, **A1 从「新建装置」降级为「指向既有装置」**。
但二者维度不同 (A1 是**取值相等**: gitlink == aria post-merge master; C2 是**可达性**:
gitlink 指向的 commit 在 master 上), 而本轮已实测**可达性对「陈旧但已合并」这个方向零拒绝能力**
⇒ **C2 不能替代 A1, 只能并存**。执行时须写清两者各守哪个方向, 不得合并成一条。

### 2.3 D2 的裁定即刻生效于本 DEC 之后的所有上呈

自本 DEC 起, 上呈选项集时**照常给推荐**, 但必须同时写:
(a) 推荐的**最强反证**; (b)「如果我错了, 错在哪里」; (c) 选项集完整性的自查依据。
判据不再是「给不给推荐」, 而是「**选项集完整吗 + 推荐带不带反证**」。
