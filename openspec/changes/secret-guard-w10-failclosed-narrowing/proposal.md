## Why

### 现状

v1.76.1 的 W10（变量展开第二遍）有三道尺寸上限，超限一律 fail-closed 拦截，文案是「Nothing was matched」。上限定义在 `hooks/secret-guard.sh` 的 `_SGV_*`：

| 上限 | 判据 | 触发后 |
|---|---|---|
| `_SGV_VMAX` = 4096 | 收集到的单个值（赋值或 for 列表）超过 4096 字符 | `_sg_vx_collect` 返回 2 → 拦，**不管这个变量有没有被引用** |
| `_SGV_SMAX` = 8192 | 代入后的副本**总长**超过 8192（整串模式下≈整条命令） | `_sg_vx_apply` 返回 2 → 拦，**数的是总长、不是膨胀量** |
| `_SGV_TMAX` = 65536 | 分段模式下各段副本的总和 | 拦 |

后果：任何超过 8 KB、引用了一个变量的整串模式命令都会被拦，哪怕展开只多出几个字符。

### 真实流量（本机 Claude Code 会话记录，2026-10-21 实测）

| 问题 | 结果 | 证据 |
|---|---|---|
| 超过 8 KB 的真实命令有多少被 W10 尺寸上限拦下 | 739 条里拦 130 条，占 **17.6%** | E12 |
| 超过 4 KB 的真实命令里，被 W10 尺寸上限拦下的 138 条按原因分 | 137 条是 SMAX（总长），全部为整串模式；1 条是 VMAX（值长）；for 列表跨行 0 条 | W1 |
| 那 137 条的真实膨胀量 | ≤ 0：2 条；1–256：60 条；257–1 K：64 条；1–4 K：10 条；> 4 K：1 条（最大 6200） | W1 |
| 那 1 条值超限 | 4594 字符的带引号赋值，**在命令其他地方没有被引用** | W1 |
| 如果放行并完整判定（含 credit）代入后的副本 | 平均 0.19 s，最慢 0.97 s；**138 条全部判为无害** | W1 |
| 只匹配规则、不算 credit 的话 | 31 条命中规则（今天靠 credit 放行），匹配平均 0.16 s | W2 |
| 代入后副本的最长行 | 中位数 566，最大 4457，**没有超过 8192 的**；那 31 条最大 2139 | W3 |

**结论**：这 138 次全是误拦，而完整判定它们很便宜。

### 8192 原本要防什么

头注释（基线 `:587` 一带）给 SMAX 的立论是：「BLOCK 判定的代价是副本长度的平方（`_sg_compute_credit` 单行：8 KB 约 0.9 s，16 KB 约 3 s，32 KB 约 13 s），晚于超时的判定会丢失」。实读与实测（#228 B.1）后，这句话需要修正：

- `_sg_compute_credit` 通过 `_sg_line_match` **逐行**匹配过滤器正则，正则里有 `.+`，所以平方级成本只跟**单行长度**有关，不跟总长。真实脚本的行都很短（W3）。（唯一的整段匹配是开头的 tight 模式检测，基线 `:476`；它的通配段不跨空白，成本受单个 token 长度约束，而 token 不会跨行，所以同样受单行长度约束。）
- 因此真正要防的，是构造出来的**超长单行**：首遍看不出（例如变量间接），第二遍命中规则后，credit 在超长单行上算到超过 5 s，判定丢失，结果 fail-open。M6 用「总长 > 8192 一律拦」防住了它，但误伤了全部大命令。

## What Changes

### 1. 增长上限代替总长上限（主项）

- `_sg_vx_apply S`：返回 2 的条件，从「副本长度 > `_SGV_SMAX`」改为「副本长度 > `${#S}` + `_SGV_GMAX`」。新常量 `_SGV_GMAX` = 8192，即代入最多让被判串增长 8192 字符。仍然是边构建边检查，超出即停，不构建超限的串。
- `_SGV_SMAX`（8192）保留，但只作为「大副本」的分界（见第 2 项），不再直接拦。
- `_SGV_TMAX`（65536）不变。
- 整串模式与分段模式同一口径。

### 2. 大副本的判定（`_sg_vx_pass`，副本长于 `_SGV_SMAX` 时）

依次执行：

1. **时间护栏**：若 `(( SECONDS * 2 >= _SG_TIME_BUDGET ))` 成立，就拦，复用 C 的时间预算文案（fail-closed）。
   - `SECONDS` 从 hook 进程启动开始计，包含首遍和收集的耗时。
   - 理由：大副本的判定与首遍判原串的代价相近。已经用掉一半预算时，第二遍很可能越过 Claude Code 的 5 s 而 fail-open。C 的 `_sg_over_budget` 从 `_SG_T0` 起算，`_SG_T0` 在首遍**之后**才重置（#228 实测），看不到首遍的耗时，所以这里不能用它。
2. **最长行 ≤ `_SGV_LMAX`**（新常量 8192）：照常调用 `_sg_judge_one`，含 credit。逐行计算 credit 的成本因此有上界。
3. **否则**（代入后出现超过 8192 字符的行）：只匹配规则，不算 credit。
   - 对 W12 中和后的副本逐条匹配 `risky_patterns`。
   - 命中就拦，文案沿用 oversize 那一套，原因串为「代入后有一行超过 8192 字符，且命中了凭据形读取；这个尺寸下不评估脱敏过滤」。
   - 不命中，这个副本就通过。

**实现约束**：

- 最长行的计算必须是线性的，只在副本 > `_SGV_SMAX` 时才做，小副本不付这份成本。
- 新 helper 定义在源码闸门之上（SC-8 时延 harness 的 W14 规则）。

### 3. 只拦被引用的超大值（`_sg_vx_collect`）

值超过 `_SGV_VMAX` 时，先看命令里（去掉这条赋值本身）有没有出现 `$NAME` 或 `${NAME}`：

- **出现了**：照旧返回 2，拦。
- **没出现**：跳过这个值（不收集），继续收集后面的。

补充说明：

- 链式引用（别的赋值的值里写了 `${NAME}`）也在命令文本里，所以算作「被引用」。
- 前缀撞名的情况，例如 `$NAMEX` 也匹配 `$NAME`，会被当作「被引用」处理。这是偏严的方向，可以接受。
- for 列表同理，看循环变量有没有被引用。

### 4. for 列表止于换行（`_sg_vx_collect` 的 for 正则）

列表部分 `([^;&|)]*)` 的字符类加入换行。这样多行 for 循环的循环体不再被当成一个「值」。

### 5. 其余

- **W9 扩展的整串检查维持原口径**（基线 `:1563` 一带，副本总长 > SMAX 即拦）。原因：扩展检查会在副本上重跑 `_sg_core_eval`，其中包括 O(n²) 的首遍扫描器，长副本确实贵；而且本机所有项目都没有启用扩展。这一点如实申报，等 #228 线性化之后再议。
- **清理死代码**：`_sg_vx_collect` 的链式循环里 `[[ -z "${_SGV_V[j]}" ]] && continue` 永远为假（收集时已经跳过空值），删掉（issue 小项）。
- **头注释**：W10 预算段改为逐行成本的立论加实测数据，并写明 `_SGV_GMAX`、`_SGV_LMAX` 的语义。

## 不变量与范围外

- **不新增 fail-open 路径**。被放行的大副本都经过完整判定，没有「跳过扫描」的路径。拦截的原因只会从「尺寸」变成以下三种之一：判定结果、时间、超长单行命中。
- **数值不变**：`_SGV_VMAX` 4096、`_SGV_SMAX` 8192（改作分界）、`_SGV_TMAX` 65536 都不变。
- **count 轴不动**：第 17 个赋值、第 9 个引用、第 9 条 for 语句起放行，仍是 fail-open。issue 建议另议。
- **其他不动**：C 的时间预算与 5 s 超时、首遍扫描（#228）、`# guard:ack` 逃生口都不变。

## Decision record

1. **先量真实流量再设计**（#228 的教训）。E12 与 W1–W3 定下了主项：137/138 是总长上限误伤，膨胀量都很小。
2. **为什么不直接调大 SMAX**：SMAX 防的是 credit 在超长单行上的平方级成本（见 Why）。直接调大会让构造的单行输入重新出现「判定迟到 → fail-open」。按最长行分流，只在真正危险的情况下保留这层保护。
3. **为什么时间护栏用 `SECONDS` 而不用 `_SG_T0`**：C 的时钟从首遍之后才开始，而第二遍判大副本的成本约等于首遍。
4. **扩展检查不改**：它在副本上重跑 O(n²) 的首遍，长副本的代价是真实的；本机没有项目启用扩展。
5. **第 3、4 项也纳入**：真实流量里分别只出现 1 次和 0 次，但它们是引用判断和解析层面的正确性问题，改动小，各自有 bf SC。
6. **count 轴不在范围内**：issue 建议维持 fail-open，因为把它改成 fail-closed 的误拦面远大于尺寸轴。
