### 实测：方案 1 对 9 类「无关换行、credit 子句本身单行完整」构造全部误伤

用 `test_v2_compare.sh` 构造：credit 子句（如 `| jq keys`、`| grep -v SECRET`、`| sha256sum`、`>/dev/null` 等）本身完整地占满一整行，但该行**前面**多了一行完全无关的内容（如 `echo Starting export`），两行之间只有一个真实换行符（无 `;`，这在 §What.2 的设计里不是切分点，所以整个两行文本是**同一个 segment**）：

```
seg = "echo Starting export\nnomad var get -out=json nomad/jobs/build-x | jq '.Items | keys'"

compute_credit_fork(seg)               = 1   ← 现状(canonical): 有 credit, 放行
compute_credit_builtin_unguarded(seg)  = 1   ← 字面直译(无守卫): 同样有 credit, 与现状一致, 无回归
compute_credit_builtin_guarded(seg)    = 0   ← 加了方案1守卫: credit 被强制清零!
```

这不是孤例。对 11 处「用 `[[:space:]]` 作分隔符」的判据（jq-keys / jq-brace / grep-anchor / grep-v / sed / cut / awk-$N / awk-regex / curl-o / wc / sha256sum）逐条构造同款「无关前导行 + 单行完整 credit 子句」，**11/11 全部**呈现 `fork=1, unguarded=1, guarded=0` 的模式（`test_v2_compare.sh` 输出，见脚本产物）。更关键的是，我追加测了 R4 报告认定「不受影响」的 `>/dev/null`（判据 383）：

```
seg = "echo prefix\ncat /opt/.env >/dev/null"
fork=1, unguarded=1, guarded=0
```

**同样中招**。这说明：R4-C-1 原始发现的 fail-open 只影响 11/13（依赖 `[[:space:]]` 作跨行桥梁的判据），但方案 1 的守卫是**段级、与具体判据无关**的粗粒度拦截（`[[ "$seg" != *$'\n'* ]]` 一旦为假，13 处判据全部被短路），所以它引入的新 fail-close 覆盖 **13/13**，比它要修的那个洞（11/13）更宽。

### 根因：`$` 锚点差异被方案 1 一并牺牲掉了

进一步定位（`test_credit_transitions.sh`）：

```
seg = "cat /opt/.env | jq keys\n"          （单行 credit + 仅尾随换行, 无后续内容）
fork=1, unguarded=1, guarded=0
```

`[[:space:]]*($|\|)` 里的 `$` 在 bash builtin 下锚定「整串末尾」；`[[:space:]]*` 会贪婪吃掉那个尾随 `\n`，所以哪怕**不加守卫**，字面直译在这个 case 上也是对的（`unguarded=1`，与 canonical 一致）。是方案 1 的守卫**主动**把这个本来正确的结果推翻成 0。这与 R4 报告分析的 B/C 案例（`0→2`，根因是 `$` 只锚定行尾/串尾的差异导致原本能匹配的东西匹配不上）是**不同机制**：B/C 是「字面直译本身就匹配不上」（`unguarded=0`），我这里发现的是「字面直译匹配得上、守卫把它打掉」（`unguarded=1, guarded=0`）——后者是方案 1**独有**的代价，不能归咎于「转内建」本身。

- SC-15 扩容 1（换行维度）新增的 3 条端到端 fixture（B/C/E）**全部是正向断言**——验证「该拦的确实拦了」（B/C 的 `0→2` 被 spec 明确接受为可容忍代价，E 的 `2→0` 被守卫修复）。**没有一条是负向断言**——验证「不该拦的没被误拦」。我这轮构造的恰恰是这类负向 fixture，且全部落空。
- SC-8 四档负载（a-d）全部不含内部换行（我重新核对了 proposal 原文对四档的定义：单条 benign / 2 段全 benign / 2 段全命中 / 3 段全命中），**结构上不可能覆盖这个方向**。

### 验证过的替代方案：判断「匹配子串」而非「整个 segment」

`credit_lib_v2.sh` 实现：不检查 `$seg` 整体，而是先让正则匹配，再检查**实际命中的子串** `${BASH_REMATCH[0]}` 是否含换行：

```bash
pat='\|[[:space:]]*(sha256sum|md5sum|sha1sum|sha512sum)\b'
if [[ "$seg" =~ $pat ]] && [[ "${BASH_REMATCH[0]}" != *$'\n'* ]]; then
  has_filter=1
fi
```

### 建议改法

1. **Task 1.3b 的强制修法从「段级换行守卫」改为「匹配子串级换行守卫」**：`if [[ "$seg" =~ $pat ]] && [[ "${BASH_REMATCH[0]}" != *$'\n'* ]]; then has_filter=1; fi`。零 fork、性能等价（已实测）、同样挡住原始 fail-open、且不再对「无关换行」类误伤。
2. **SC-15 扩容 1 补齐负向方向**：至少把本报告 §组3 的 7 类判据的「无关前导行 + 单行完整 credit」构造写死为 fixture（断言改后**仍给** credit，即 exit 不变），反事实：段级守卫（方案 1）实现 → 这些 fixture 全部翻红；匹配子串级守卫（v2）→ 全部保持绿。这组 fixture 与已有的 B/C/E 三条方向互补（B/C/E 锁「该拦的确实拦」，新增的锁「不该拦的没被误拦」），两组合起来才是完整的 SC-15 换行维度覆盖。
3. **若 owner 仍偏好方案 1（实现更简单）**，至少需要在 spec 里明确记录并接受这个代价（比照 B/C 案例的处理方式：写成「已知代价，spec 主动接受」），而不是像现在这样完全没有意识到它的存在。

## 自我确认风险：诚实拆分「作者照我说的改了」与「这个改法本身经得起攻击」

```
$ 另有 1 处裸 `.+`（L342 的 `(.+\|[[:space:]]*)?`）——方案 2 若要彻底堵住跨行匹配，

```

所以「13 倍」这个具体倍数是**未经验证的断言**（实测应为约 30/13 ≈ 2.3 倍的字符类改写点，而非 13 倍），属于 memory `feedback_never_write_unverified_impossibility_claims` 点名的模式在数字断言（非「不可能」断言）上的变体——不应该在没算过的情况下把一个具体倍数写进 spec 论据。**但方向性结论未必错**：方案 2 需要对 29+ 处字符类逐条判断「这处 `[[:space:]]` 是否真的需要保留跨行语义」（有的地方或许故意想保留一定容忍度），这是**逐条定制、审查成本高**的工作，而不能像方案 1（或我这轮验证的 v2）那样写一次通用逻辑机械套用 13 次。真正的结论应该是「方案 2 工程量与出错面显著大于方案 1/v2，但不是 13 倍那么精确的数字」——建议 spec 把「13 倍」改成「约 2-3 倍改写点且需逐条定制审查（非机械套用）」，或者直接删除具体倍数只保留定性判断。

## 换行守卫「每条判据前置」与「入口一次判断」的等价性核查

任务 brief 要求核实这两种放置方式是否等价、spec 措辞是否有歧义。结论：**语义完全等价，spec 措辞本身无歧义**。

- 「每条判据前置」= 13 次重复 `[[ "$seg" != *$'\n'* ]] && [[ "$seg" =~ $patN ]]`；「入口一次判断」= 在 has_filter 计算开始前做一次 `[[ "$seg" == *$'\n'* ]] && { echo 0; return; }`，跳过全部 13 处判据。两者对任意输入产出的 `has_filter` 值**完全相同**（只要该「入口判断」只作用于 has_filter 计算范围，不越界影响 guard:ack 检测等其他逻辑）。差别仅在于实现风格与极小的执行路径开销（含换行时，「入口一次判断」可以提前短路省掉后续判据的正则匹配尝试，「每条前置」则每条都要重新做一次字符串包含检查——但两者都是 O(1) 操作，量级上不构成有意义差异，`bench_guard.sh` 的 D 档实测也印证了这点：方案 1 的短路让它在含换行负载上比 v2 略快，差距在 1ms 以内）。
- spec 正文（`Task 1.3b`：「每条判据前置」）与 SC-15 扩容 1（「受影响的 11 处各加 1 条」）在措辞上是一致的，都是「逐条」视角，没有自相矛盾之处。**这一点上没有发现问题**。

## 实现可行性：换行守卫 + `(^|\n)` 改写 + 保留 `\b` 三者叠加

- 三处改动的**作用域互不重叠**：换行守卫作用于 13 处 `has_filter` credit 判据（§What.4 范围）；`(^|\n)` 改写作用于 `safe_to_split()` 内「命令位置」检测的行首/换行后 2 类（§What.1 范围）；`\b` 保留是对 141 条 `risky_patterns` 与 13 处 credit 判据里已有的 `\b` 用法维持不变（§6 范围）。三者分别修改不同的正则片段，不存在同一段正则被两条约束同时要求的冲突。
- 三者均为纯 bash builtin 字符串/正则操作，均不引入 fork——本轮的性能实测（`bench_guard.sh`/`bench_e2e_sc8.sh`）已经覆盖「换行守卫」这一项，`\b` 保留不改变实现方式（本来就是直接保留，无新增操作），`(^|\n)` 改写是 `safe_to_split()` 内部的正则拼接，同样是 O(1) 字符串操作，量级上不会撼动 SC-8 的结论。
- 结合本轮 CRITICAL-1 的建议（用 `${BASH_REMATCH[0]}` 替代整段 `$seg` 做换行检查），实现复杂度略高于方案 1（需要先匹配、再检查 `BASH_REMATCH`，而不是前置短路），但仍是标准 bash 语法，**语义可用「匹配后置检查」这一条统一规则表达，不需要像方案 2 那样逐条定制**，工程量与方案 1 相当。

**结论：除本轮 CRITICAL-1 指出的换行守卫粒度问题外，三处实现约束叠加后依然可行、零 fork、语义可验。**

## 总体判定

**REVISE**。

正面结论（本轮独立复验后可采信）：R4 的两条 Critical 中，`^`/换行位置检测问题（CRITICAL-2）的修法经检验无新问题；SC-9 双腿裁定完整落地；SC-8 性能结论在加了换行守卫之后，用两种不同的守卫实现独立复测，均保持大幅净减少（-68%~-88%），远超 50% 闸值，R4 三席的判断本轮进一步夯实。

但 R4-fix 为修复「13 处转内建的 fail-open」（我 R4 自己提出的方案）引入了一个**新的、覆盖面比原问题更广的 fail-close 缺口**：段级换行守卫会让任何「无关换行 + 单行完整合法 filter」的常见多行命令从允许变为拦截，13/13 处判据无一幸免，现有 SC-15 扩容（B/C/E 三条）与 SC-8 四档结构上都测不到这个方向，因为它们全部是「正向锁定该拦的确实拦」，没有「负向锁定不该拦的没被误拦」。这是本 cycle 第五次「勘正动作本身引入新错误」，这次的勘正者是我自己（backend-architect R4→R5）。

我已经验证并提供了一个可直接采纳的修法：把「检查整个 segment 是否含换行」改为「检查正则实际命中的子串（`${BASH_REMATCH[0]}`）是否含换行」，零 fork、性能与方案 1 相当（已实测）、同时挡住原始 fail-open 且几乎不产生新的 fail-close（仅残留一个更窄的「纯尾随换行」边界形态）。这个修法只需要把 Task 1.3b 与对应的 13 处实现从「前置 `&&` 短路」改成「匹配后检查 `BASH_REMATCH`」，改动量与方案 1 相当，不需要引入方案 2 那种逐条定制的工程量。

本轮建议 owner 裁定：Task 1.3b 改用「匹配子串级」换行守卫（而非「段级」），SC-15 补齐负向 fixture（至少覆盖本报告列出的 7 类判据的「无关前导行」构造）。这两处改法都是文字/实现细节级别，不改变 v4/v5 的整体设计方向（fail-safe 降级 + 先 pattern 后 credit + 13 处转内建），预计可以在不需要 R6 的情况下由 owner 直接裁定后进入 Phase B——但因为这是一个新发现的、覆盖面广的 Critical，我不建议在没有 owner 明确表态前默认可以直接进 A.2。
