### [MAJOR] 「必须能解析为非负整数」未钉到字符级 —— `int()` 派与 `isdigit()` 派对 `#+7` / `#1_000` / `# 122` 结论相反

- **位置**: `proposal.md:56` (步骤 2) / `:53` (比较键) / `:110` (SC-6 清单)
- **问题**: `:56` 一句话里给了**两个不同层次**的判据且互不等价: 前半「`number_str` 必须能**解析为非负整数**」像是谓词校验, 后半「**解析为 `int`** 后比较」像是直接调 `int()`。Python 的 `int()` 接受的语法远宽于「数字串」, 两种读法在真实输入上给出相反匹配结论。
- **证据** (本机 Python 3.11.2 实测):

  | `number_str` | `int()` | `.isdigit()` | `re.fullmatch(r"[0-9]+")` |
  |---|---|---|---|
  | `+7` | `7` | False | False |
  | `1_000` | `1000` (PEP 515) | False | False |
  | ` 122` (前导空格) | `122` (`int` 自带 strip) | False | False |
  | `١٢٢` (阿拉伯-印度数字) | `122` | **True** | False |
  | `"9"*5000` | **ValueError** (3.11 起 4300 位上限) | True | True |

  - 对拍实测 (X vs Y → A 结果 / B 结果): `aria-plugin#+7` vs `aria-plugin#7` → **命中 / 不命中**; `aria-plugin#1_000` vs `aria-plugin#1000` → **命中 / 不命中**; `aria-plugin# 122` vs `aria-plugin#122` → **命中 / 不命中**。三对全部分叉。
  - 加重因素之一: `:110` 的不可解析清单只给了 `repo#abc` 这一种「完全不像数字」的例子, 没有一个**边界**例子, 读者无从反推作者意图。
  - 加重因素之二: 同一份规格 `:58` 刚刚赋予 `_` 「一律译为 `-`」的语义 (仅限 basename), 更会诱导实现者认为 number 侧的 `_` 也是良性的。
  - 加重因素之三: 超长数字串使**同一份实现**在 Python 3.10 与 3.11 上行为不同 (3.11 抛 ValueError ⇒ 落入不可解析分支), 违背 `track_id.py:80-83` 为归一函数立下的「跨容器确定性」标准。
- **建议修法**: 把 `:56` 改成字面正则, 消除全部自由度。建议: 「`number_str` 必须满足 `re.fullmatch(r"[0-9]{1,9}", number_str)` (**显式 ASCII 数字类**, 从而排除 `+`/`-`/`_`/空白/Unicode 数字/超长串), 否则不可解析; 满足后取 `int(number_str)` 作为 `number`」。并在 SC-6 的清单里补齐四个边界 fixture: `repo#+7` / `repo#1_000` / `repo# 7` / `repo#١٢٢` —— 有了它们, 上述三对分叉就都被钉死。

### [MAJOR] 规则 4 的「原字符串」= 剥空白前还是后, 未定义 —— 两实现者对带空白的不可解析值结论相反

- **位置**: `proposal.md:62` (规则 4) / `:55` (步骤 1) / `:89` (D3)
- **问题**: `:55` 步骤 1 已「剥首尾空白」, `:62` 却说「退回**原字符串**精确比较」。「原字符串」有两个同样自然的所指: (a) 传入的 raw 值; (b) 步骤 1 处理后的串。规格未择一, 且**现状代码支持 (a) 的读法**——`collision.py:217` 就是对 raw 值做 `!=`, 读者很容易把「退回原串」理解成「保持今天的行为」。
- **证据**:
  - `:62` 原文: 「**不可解析的值** ⇒ **不参与归一, 退回原字符串精确比较**」。
  - 对拍实测: X = `'no-hash-here'`, Y = `' no-hash-here '` → **A (raw) 不命中 / B (剥后) 命中**; X = `'repo#abc'`, Y = `' repo#abc '` → **A 不命中 / B 命中**。结论相反。
  - 该输入不是臆造: 三族表 `:33` 的 C 族本身就是「AI 从 proposal 头部字段逐字照抄」而来, 抄进 YAML 标量时带尾随空格是常态; `:57` 专门为 `#` 前的空格加了一条剥离规则, 说明作者已知空白是现实问题 —— 唯独在 fallback 分支漏了。
  - 次生歧义: `:62` 也未说明 fallback 是否 casefold。若按「精确」取区分大小写, 则会出现 `REPO#5`≡`repo#5` 命中而 `REPO#abc` vs `repo#abc` 不命中的不对称 —— 该不对称本身可接受 (D3 的论域划分不受影响), 但必须写明, 否则实现者会「顺手统一」成 casefold。
- **建议修法**: `:62` 改为单一读法并写死大小写策略, 例如: 「退回**步骤 1 剥空白后的串**做**区分大小写**的精确比较 (fallback 分支**不** casefold, 与可解析侧的 casefold 语义有意不同)」。同时在 SC-6 增一条 fixture: `'repo#abc'` × `' repo#abc '` → 期望值按所选读法钉死。（注: D3 `:89` 关于「两类不可能跨类相等, 不破坏传递性」的结论**经复核成立** —— 可解析性是输入串的确定性函数, 论域确被干净划分, 该结论不受本条影响。）

### [MINOR] S5 条款的理据链与 Spec 自身另外三处断言不一致 (对齐论证只在半边成立 / 折叠算子不同 / 极性全称句被推翻)

- **位置**: `proposal.md:58-61` (S5 及其理据) / `:53`,`:63` (casefold) / `:69` (basename 轴极性) / `:88` (D2)
- **问题**: 「顺序」这一项经实测**无问题**（见下）, 但支撑 S5 的理据有三处与 Spec 别处互斥。理据与条款不一致时不能默认条款对 (memory `feedback_rationale_formula_contradiction_is_signal`)。
- **证据**:
  1. **顺序无关 (非 finding, 记录以免后续误改)**: `.`/`_`→`-` 的译码既不产生也不消耗 `/`, 因此与「按最后一个 `/` 切分」可交换。实测 `10CG/a.b#5` × `10CG/a-b#5` 在「先译后切」与「先切后译」两种实现下均为**命中**, 归一键都是 `('a-b', 5)`。规格 `:58` 把子款挂在「`repo_basename` 内的」措辞上, 语义清楚, 无需再钉。
  2. **对齐论证只在半边成立**: `:59` 的理据是「既有 `derive_track_id` 已经把 `/` `.` `_` 全译成 `-`, 若只做 casefold 则两层归一不一致」。实读 `aria/skills/state-scanner/lib/track_id.py:70-71` 确认该函数把 **`/` 也**译成 `-` 且**保留 org** (`10CG/aria-plugin` → `10cg-aria-plugin`)。而本 Spec `:57` 是**丢弃 org**。也就是说同一条「与 derive_track_id 保持一致」的理据, 若承重, 会推出「org 应当参与匹配」, 与 D2 (`:88`) 相反; 若不承重, 则 S5 的理据只剩「`10cg.local` 是真实仓」这一条。理据被选择性使用了半边。
  3. **折叠算子不同**: `track_id.py:70` 用 `.lower()`, 本 Spec `:53`/`:63` 用 `.casefold()`。二者对非 ASCII 不等价 (实测 `'ß'.lower()` = `ß`, `'ß'.casefold()` = `ss`) ⇒ 「与既有归一对齐」在大小写维度上也不精确。
  4. **极性全称句被自己推翻**: `:69` 断言「本机制在 basename 轴是 fail-toward-silence, 与 org 轴方向相反」—— 但 S5 让 basename 轴对「分隔符型」子类变成 fail-toward-**reporting** (SC-5b `:109` 正是要求命中)。该全称句在 S5 之后已不成立。
  5. **完备性前提缺失**: 合并 `.`/`_`/`-` 的正确性依赖一条否定性断言 ——「同 org 下不存在仅以分隔符相异的两个**不同**仓」。Spec 只给了存在性证据 (`:60` 「11 个 open issue」), 未给这条完备性断言; 而 `:60` 自己刚记录过同类完备性判断出错的先例 (R3 的仓名清单不完整)。旁证: 该组织确实混用分隔符 —— `docs/handoff/2026-05-31-lsp-provisioning-10cg-env-init.md:54` 同时出现 `10cg-local-plugin` 与 meta-repo `10cg.local`。(本轮环境内 Forgejo API 不可达, 未能实拉仓名清单核验。)
- **建议修法**: (a) `:59` 的理据改成只声称其真正成立的范围 ——「在**分隔符**维度与 `derive_track_id` 对齐」, 并补一句说明 org 维度为何有意不对齐 (指向 D2), 消除理据自相矛盾; (b) `:69` 改为限定句 ——「basename 轴对**截断型**别名 fail-toward-silence, 对**分隔符型**已归一」; (c) 明写完备性前提及其核验方式 (拉一次 org 仓名清单, 对 `.`/`_`→`-` 后有无重名做一次实测并留证), 或明写「若出现分隔符相异的不同仓, 按 D2 极性视为可接受误报」; (d) 若无特殊理由, 把 `:53`/`:63` 的 `casefold()` 改为 `lower()` 与 `track_id.py:70` 严格对齐 (或反之在 Spec 里说明为何有意不同)。

## 判定理由

Spec 的**动机链、缺陷定性、极性推理、决策记录结构**质量高, 且 `:153-159` 的闸门处置符合 Rule #10 (提请 owner 裁而非自行降级)。但按「两个独立实现者会不会写出同一个东西」这一唯一验收视角:

- 有 **1 处联立无解** (SC-4 vs 步骤 3 vs SC-6) —— 任何实现都必有一条 SC 红, 无法交付;
- 有 **1 处承重兜底无落地路径** (D2 回显原串, 三条通路被三处条款各堵一条, 且无 SC 兜底) —— 一个实现者会静默省略它, 另一个会为它改 SKILL.md 从而翻转 Rule #6 判据;
- 有 **3 处字符级自由度** (整数判据 / fallback 原串 / 分段空白) 在实测中给出**相反**匹配结论。
