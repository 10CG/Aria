## 2. 缩范围后实现面技术复核

原型 (纯 bash, 逐字符扫描, 单/双引号 + 转义感知, 仅切顶层 `;` `&&`) 对拍以下语料, 全部行为符合预期:

- SC-5 列出的 8 条: 单命令/`a;b`/`a&&b`/`a|b`(不切)/单引号内`;`(不切)/`\;`(不切)/换行(不切)/`a&b`(不切) — **全部正确**。
- SC-4 三条 quote-aware 锚点 (ssh find `\;` / python -c 内嵌 `;` / R1 给的 `python3 -c 'import os; print(open("/opt/.env").read())'`) — **全部正确保持单段**。
- **`&&` 消歧** (本轮任务重点): `&>`、`>&`、`|&`、`2>&1` 均不误配为 `&&` 分隔符, 且复合场景 (`a &>out.log && b`、`a 2>&1 && b`) 正确只在真 `&&` 处切 2 段 — **确认可行, 与 owner 裁定「`&` 转出因与 `&>` 等冲突, 但 `&&` 本身需字符级前瞻消歧」一致**。

**但**: SC-5 当前的 8 条断言**未覆盖**两个真实存在的实现分支, 而这两个分支恰是本轮任务点名要核实的高风险点:

- **`&&` vs `&`/`&>`/`>&`/`|&`/`2>&1` 消歧** — SC-5 无一条断言这个。我的原型验证"可行", 但"可行"是我这份 ~90 行原型的结论, 不是 Phase B 实现的保证; 一个用简单子串搜索 `&&` (未做 lookahead 排除 `&>` 场景本身不会误报, 但若实现改用其他启发式, 如"扫到 `&` 就试探性切", 则会误配) 落地的实现完全可能通过 SC-5 现有 8 条却在这个分支上错。
- **双引号内 `;`/`&&` 保护** — SC-5 8 条只测了单引号情形 (`a; b` 但 `;` 在单引号内), 未测双引号。proposal §2 引用的 R1 M-5 fixture (`python3 -c 'import os; print(open("/opt/.env").read())'`) 外层是单引号, `#157`/`#152` 等既有语料也未见双引号包裹分隔符的组合。双引号的转义规则 (`\ $ \` "` 才转义, 其余字面) 与单引号 (零转义) 是两套不同状态机分支, 缺失覆盖意味着这条分支实现错了也不会被 SC-5 抓到。

→ **MAJOR-1**: 见下方详述。

## 3. `;`/`&&` 缩范围下 has_filter 13 处 subprocess 实测增量

方法: 提取 `has_filter` 判据块 (`secret-guard.sh:323-397`, 原样未改) 为独立函数, 驱动脚本模拟 §4 伪代码 (逐段 `compute_credit` 短路 + 全 141 pattern builtin `[[ =~ ]]` 扫描), "before" = 现状整条命令求值一次, "after" = 按缩范围段数逐段求值。**用 `user+sys` (CPU time) 而非 `real`, 因为本机 load average 6.5+ 下 `real` 在同一 shell session 内连续 3 次同参数试验就能从 6.08s 摆到 14.26s (同一份代码, >2倍摆幅) — 这正是 R1 MAJOR-2 点名的噪声, SC-8 当前文本"同一次会话内取中位数"并**未**显式要求用 CPU-time 口径, 光取中位数不足以消除这个量级的噪声。**

2-段真实语料 (`echo hi; env`, 对应 `#152 mid ; env` 系列, 是 52 条 `expected=2` 用例里最简单/最典型的形态 — 就是"一条命令带一个顶层分隔符"这个最主流场景, 不是极端尾部情形):

```
3 轮独立试验 (每轮 30 次迭代, CPU time = user+sys):
  before (整条求值一次): ~44.4ms/次 (44.9/44.4/44.4, 高度稳定)
  after  (2 段各求值一次): ~84.2ms/次 (83.2/84.4/85.1, 高度稳定)
  增幅: 3 轮一致 +85% / +90% / +92%
```

3-段语料 (`echo hi; env; echo done`, 对应 `#152 env then ; more`): before ~44ms, after ~122ms, 增幅 ~+177%。

**结论**: 即便只切 `;`/`&&` 这个最小子集, **单是 2 段这种最主流的典型命令形态, has_filter 块 CPU 耗时就稳定多出约 85-92%**, 远超 SC-8 的 ≤50% 阈值; 且这个数字在 3 轮独立试验里高度一致 (非本机偶发噪声), 不是尾部情形才踩中——是"任何一条带顶层 `;` 或 `&&` 的命令"都会踩中的**主流形态代价**。

→ **MAJOR-2**: 见下方。

## MAJOR-1: SC-5 缺 `&&`/`&`/`&>`/`2>&1` 消歧断言 + 双引号保护断言

本轮任务点名要核实的"`&&` 识别不得误配单 `&` 与 `&>`", 我的原型验证**设计上可行**, 但这不等于**实现上有保证**——SC-5 现有 8 条断言里没有一条覆盖这个分支, 也没有覆盖双引号内 `;`/`&&` 保护这个分支。SC-5 存在的目的 (proposal §Tasks 明文: "防「切错但被兜住」") 恰恰是为了不依赖"我这轮审计验证过可行"这种一次性证据, 而是把正确行为**锁进回归测试**。当前 8 条锁不住这两个分支。

**建议**: SC-5 补至少 2 条:
- `a &>out.log && b` (或更简写法) → 2 段, 且 `&>` 不被误当分隔符
- `a; "b;c"; d` (双引号包裹 `;`) → 3 段, 双引号内 `;` 不切 (对称地也建议补一条双引号内 `&&` 不切)

## MAJOR-2: SC-8 的 ≤50% 阈值在缩范围后仍不现实, 与转出 6 的裁定存在自相矛盾

owner 已裁定 `has_filter` 13 处 subprocess 重构**本版不做** (转出 6), 但 SC-8 仍要求实测增幅 **≤50%** 才算过 (Success Criteria 里是打勾项, 非仅记录项)。本轮实测 (见上) 显示: 缩到最小范围后, has_filter 块本身在**最主流的 2 段命令**上就已稳定造成 +85~92% 的 CPU 时间增量——这不是"极端 4 段" 才会踩中的边缘代价 (R1 CRITICAL-1 用的是 4 段样例), 而是"任意一条真正触发本 spec 修复目标的命令" (只要带 `;` 或 `&&`) 都会踩中的**主流代价**。

这意味着 **Tasks 1.1-1.7 即便完美实现, SC-8 大概率仍会转红**——因为把 SC-8 卡在 ≤50%, 事实上是在变相要求 Phase B 偷偷把转出 6 的活也干了 (否则通不过), 这与 owner"性能重构本版不做, 归转出 6"的裁定直接冲突。

**建议** (三选一, 由 owner/收口者定): (a) 仿照 SC-7 的处置方式, 把 SC-8 从"必须 ≤50%"改为"如实记录实测数字 + 若超阈值须显式标注为转出 6 的已知代价, 不阻塞本 spec 验收"; (b) 明确把 has_filter 的**最小化**改动 (不是完整 O3 重构, 只是把 13 处挪出循环、每段只算一次而非重复算某些恒定判据——若确有更省的做法) 纳入 Task 1.1/1.2 范围; (c) 维持 ≤50% 硬门槛, 但显式接受"SC-8 大概率本轮转红, 待转出 6 单独 ship 后收口", 写进 Success Criteria 原文而非留给 Phase B 实现者自行发现。**不建议**保持现状 (阈值写死 ≤50% 且未标注预期后果) —— 这会让 Phase B 在验收阶段撞上一个 spec 自身埋的矛盾, 重演本 spec 前身 (归档 proposal) 因表述不诚实而返工的同类问题。
