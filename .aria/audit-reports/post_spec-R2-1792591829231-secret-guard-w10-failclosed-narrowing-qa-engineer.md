**QA2-F01** — type: issue — severity: **Major** — category: testing — scope: SC-N5c、SC-N9（亦波及 SC-N9 的 `watch` 例） — **新**

一句话：「对抗形状」没钉死读取目标与赋值位置；用套件惯用的 `wpa_AI`（app.ini 路径）且赋值放首行时，这个形状根本不对抗：SC-N5c 在**好实现上红**，SC-N9 抓不到无计时杀的坏实现。

证据（`lib/slow.sh`、`lib/shapes.sh`，bash 5.2，好实现）：

- k=5 行 8000 字符 token 加经变量的读取，默认预算：读取目标是 app.ini 路径且 `f=` 在首行 → **finding，0.56 s**（解释：`tight` 检测的 `[[ =~ ]]` 是搜索，路径在串首就命中则不必对长 token 做失败扫描；赋值挪到末尾即变慢，与此解释一致）；`f=` 放在 token 行之后 → **time，3.28 s**；读取目标换成不被 `_SG_SRVCFG`/`_SG_CLAUDE_CFG` 命中的凭据路径（运行时拼装），首尾赋值皆 **time，3.25–3.27 s**。
- SC-N5c（预算 1）同一形状「app.ini 路径、赋值居首」：好实现连跑 10 次，**1 次 time（0.24 s）、9 次 finding（0.54–0.74 s）**——出 time 的那次是 `SECONDS-P0` 恰好读到 1、`left<=0` 直接拦；其余判定在截止内跑完。期望「时间模板」只在凭据路径形状下确定成立（time，1.27–1.29 s 或 0.25 s，二者皆过 2.5 s 界）。
- SC-N9 的 `watch` 例：基线首遍（`oversize` 拦截的 wall）n=500 / 750 / 1000 / 1500 行为 0.54 / 1.27 / 2.06 / **4.03 s**；规格写的 1500 行违反它自己的「首遍 < 1 s」，好实现 4.22 s 出 time（`left<=0`，没有走到杀判定那条路）。n=500–1000 时判定在截止内跑完（finding），杀路径同样没被走到。即 `watch` 例在其前提内**构造不出**「判定超截止」。k=3 的 token 例也是 finding（2.73 s，判定在截止内完成）。真正走杀路径的只有 k=5、k=8（凭据路径形状）。
- 无计时杀的坏实现（#11）：k=3 / 5 / 8 的 wall 为 3.33 / 4.90 / 7.59 s，5 s 界下只有 k=8 红。

建议：钉死形状——读取目标须是不被 tight 检测早命中的凭据形路径（运行时拼装），或把赋值放在 token 行之后；用例内加**前置断言**：对该副本直调基线 `_sg_judge_one` 须 > 4 s（形状漂移时红，而不是悄悄绿）。杀路径另加确定性版本：直调 `_sg_vx_big`，把 `_sg_vx_big_judge` 换成空转函数，预算 1，期望返回 3 且 stderr 为空（实测好实现返回 3、stderr 空，不依赖主机速度与形状）。`watch` 例改成「首遍实测 < 1 s 的行数」，并写明它只覆盖「在截止内完成」。
