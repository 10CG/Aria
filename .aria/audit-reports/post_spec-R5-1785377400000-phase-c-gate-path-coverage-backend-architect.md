## Findings

### [CRITICAL] D12 判据缺「按 `:` 拆键值」步骤 ⇒ 同行 `key: &anchor` / `key: *alias` 这一最常见写法反而**检测不到**

- **位置**: `openspec/changes/phase-c-gate-path-coverage-not-applicable/proposal.md:63` (D12 判据本体) / `:149` (D12 决策行) / `:202` (SC-30)
- **问题**: `:63` 给出的 4 步流水线 —「剥行尾 `#` 注释 → strip → 剥块序列标记 `- ` → 剥成对首尾引号」— 全部作用在**整行字符串**上, 从未把一行拆成「键」和「值」两个子串。可是判定条件写的是「**值或键**的首字符为 `&`/`*`/`!`, 或**键位**以 `<<` 开头」—— 这暗示存在两个独立的检查目标 (键/值), 但前面 4 步从不产生这两个目标, 只产生**一个**变换后的字符串。对形如 `push: &common_trigger` 这种**锚点直接挂在同一行 key 后面**的标准 YAML 写法 (anchor 最主流的书写方式, 也是 push/pull_request 共享触发配置的常见 DRY 手法), 4 步流水线的输出仍是 `push: &common_trigger` 本身, 首字符是 `p`, 永远无法命中 `&`/`*`/`!`/`<<` 中任何一个。这恰恰是 D12 存在的理由要防的那类构造——「无法安全解读的 YAML 特性」——却被它自己的判据放过。
- **证据** (把 `:63` 的 4 步逐字翻成 Python, 无任何额外的键值拆分步骤, 直接跑):

  ```
  False  push: &common_trigger        <- 锚点挂在 push 触发定义上 (real-world 复用 push/pull_request 触发的写法)
  False  pull_request: *common_trigger <- 引用同一锚点
  False  paths: &p                     <- 锚点直接挂在 paths 键上
  True   <<: *base                     <- 合并键场景, 因为"键本身"就是 << (巧合, 见下)
  True   - *alias / - &x               <- 块序列裸值 (无 key 前缀), 剥完 "- " 后就是整个"值"
  ```

  `<<: *base` 之所以命中, 纯属巧合 —— 因为它的**键本身**逐字符就是 `<<`, 检查「整行是否以 `<<` 开头」等价于检查「键是否是 `<<`」。但 `push:`/`pull_request:`/`paths:` 等**普通键 + 该键的值带锚点/别名**这种同样常见、且是 SC-30 正控声称必须覆盖的形态 (「`&anchor`/`*alias`/`<<`/`!tag` **落在 `on:` 子树内**」—— 未限定必须是裸值行), 4 步流水线系统性漏判。
  **交叉证据 (本轮 R5 tech-lead 报告独立复现的分歧)**: tech-lead 席位在同一 A1 上跑了一份自己的 D12 参考实现, 其测试表把 `push: &push_cfg` 判为 **HIT=True**(与本文的 `push: &common_trigger` 结构完全等价, 结果却相反)。两份完全独立、都自称"照 `:63` 字面实现"的脚本, 对**同一类输入**给出**相反**结论——这正是「两独立实现者同规格得相反结果 = 欠定实锤」(memory `feedback_spec_underdetermination_two_implementer_test`, 且 D12 自身的引入理由 `:64` 就是在关闭同一形状的欠定「本 Spec 原文只写「anchors → covered」未定判据, 属欠定」)。`:63` 没有给出"如何从一行里分离键与值"这一步, 两个显然都合理的实现路径 (「整行首字符」vs「冒号后取值再首字符」) 因此都能自称忠于原文。
- **建议修法** (与危害同向: 让判据真正覼盖它自称要盖的输入, 而不是繼续留一个可以各表一套的缺口):
  1. 在 `:63` 明确加一步: 在「strip」之后、「剥块序列标记」之前, 先判断该行是否存在**顶层 (不在引号/flow 集合内) 的首个 `:`**; 若存在, 把行拆成 `key_part` (冒号前) 与 `value_part` (冒号后), 分别 strip; 之后「剥引号」「首字符判定」对 `value_part` 执行 (若非空), 「`<<` 判定」对 `key_part` 执行; 若不存在 `:`(块序列裸值 / 纯 scalar 行), 沿用现有整行判定。
  2. SC-30 (`:202`) 正控增补至少一条**同行 `key: &anchor` 形态**的用例 (如 `push: &shared` 或 `paths: *shared_paths`), 使该分支不再只靠裸值行 (`- *alias`) 和巧合命中的 `<<:` 撑起「4/4 通过」的假象。

### [CRITICAL] D12「剥成对首尾引号」只会扩大命中面 ⇒ 带引号的 leading-`*`/`!` glob (GHA 官方文档形态) 被误判为构造级不确定, 恒 wait 复发

- **位置**: `:63` (D12 判据第 4 步) / `:149` (D12 决策行) / `:202` (SC-30 负控)
- **问题**: YAML 里被引号包裹的标量**永远**是字面量, 不可能是 anchor(`&`)/alias(`*`)/merge-key(`<<`)/tag(`!`)。但 D12 第 4 步偏偏先把引号剥掉, 再检查首字符——这就让**任何以 `*` 或 `!` 打头的合法 glob 字符串**(`'*.py'`、`'**.js'`、`'!docs/**'`) 在剥引号后首字符正好是 `*`/`!`, 被误判成「构造级不确定」→ 该 workflow 强制 `covered` → gate 对这类仓库恒 wait。`**.js`/`*.py` 形态的 leading-wildcard glob 不是我编造的边缘案例——GHA 官方 `paths` 文档本身就用这类写法做示例, 属于会被真实采用者书写的标准形态。
- **证据** (按 `:63` 字面实现, 对本仓语料 + 反例逐行判定):
  ```
  False   "- 'skills/issue-triage/**'"          本仓语料 (目录名打头, 安全)
  False   "- 'aria-orchestrator/docker/aria-runner/**'"  本仓语料 (同上)
  False   "paths: ['a/**']"                     SC-30 负控 (iii), 目录名打头
  True    "- '*.py'"                            leading-* glob (GHA 文档形态) → 误判 HIT
  True    "- '**.js'"                            leading-** glob (GHA 文档形态) → 误判 HIT
  True    "- '!docs/**'"                        否定 glob → 误判 HIT, 且与既有 `:68` matcher 层「否定 `!` 一律判匹配 → covered」的既有职责重叠/抢跑
  ```
  本仓 4 份真实语料**全部**以字面目录名开头 (`skills/...`、`aria/...`、`aria-orchestrator/...`), 从未出现 leading-wildcard glob, 所以 SC-2/SC-3/SC-19/SC-20/SC-23 这些拿本仓语料回归的用例**结构上测不出这个洞**——语料是偶然安全的, 不是判据本身安全。SC-30 (`:202`) 唯一提到 glob 的负控 (iii) 特意选了 `'a/**'` (不以 `*` 开头), 同样绕开了这个组合。
  这与 `:64` 引用类比的 L 侧原始 bug 是**同一形状、同一根因**: L 的子串读法把「任何带 `*` 的行」都当命中, D12 把范围收窄到「剥引号后以 `*` 开头的行」, 但 leading-wildcard glob 恰好落在收窄后仍然命中的子集里——`:64` 自己给的诊断「把病从假绿搬到恒红, 按本 Spec §Why 自己的判据同样零信息量」对这个残留子集依然成立。
  **本轮 R5 tech-lead 报告独立复现了同一根因** (其 CRITICAL #2, 用更大的 12 条用例表格得出一致结论: `'**/*.md'`/`'*.py'`/`'"**.js"'`/`'!docs/**'` 全部误判 HIT), 与本文相互印证, 属两个独立席位对同一缺陷的收敛命中, 非重复计数。
- **建议修法** (与危害同向: 让判据只咬真正的 YAML 构造, 不再连坐带引号的字面量):
  1. 反过来定规则: **带成对引号的标量一律视为字面量, 永不参与构造级判定** (依据: anchor/alias/tag/merge-key 语法上不可能被引号包裹) —— 即「剥成对引号」这一步的产物如果确实来自「剥了引号」, 就直接跳过首字符判定, 不是继续拿剥完的内容去判。
  2. 未加引号的裸值分支, 把命中条件从「首字符是 `&`/`*`/`!`」加严为「`&`/`*` 后必须紧跟合法锚点名字符 (`^[&*][A-Za-z_][\w-]*$`)」, 排除 `**`、`*.py` 这类明显是 glob 而非 YAML 语法的形态; `!tag` 同理排除 `!!seq`/`!docs` 等非 tag 语法。
  3. SC-30 (`:202`) 负控增补: `- '*.py'` / `- '**.js'` / `- '!docs/**'` 三行落在 `on:` 的 `paths:`/`paths-ignore:` 序列内 → 不触发构造级命中 (各自独立可红)。

### [MAJOR] D13 (`---`) 从未声明扫描区间, 而其语义决定了区间不可能等于 D12 的「`on:` 块」——两条紧邻的新规则各用一个未言明、且互不相同的区间

- **位置**: `:65` (D13 判据本体) / `:63` (D12 判据, 对比) / `:150` (D13 决策行) / `:203` (SC-31)
- **问题**: D12 明确写了区间「对**区间**内每一行」(区间 = `on:` 键行到 `on:` 块结束, 沿用既有非 A1 文本的界定)。D13 与它并列插在同一份 bullet 列表里, 却完全没有类似的区间声明——只说「列 0 的 `---` 出现在**首个非空非注释内容行之后**才是多文档分隔」。`---` 是 YAML **文档级**语义, 与它在哪个嵌套块下毫无关系; 「首个非空非注释内容行」这个锚点天然是**整个文件**范围的 (典型 workflow 文件里, 那一行通常是文件顶部的 `name:`, 远在 `on:` 之前)。这意味着 D13 若要成立, 检测窗口必须覆盖到 `on:` 块结束之后 (乃至 `jobs:` 之后) 的行——与 D12 明确限定的「`on:` 键行到 `on:` 块结束」是两个不重合的区间, 全文没有一句话告诉实现者「这两个新规则分别扫描不同范围」「D13 需要额外一次全文件扫描」「两者在同一个逐行循环里如何共存」。
- **证据**:
  1. **反例构造 + 真实 YAML 语义验证** (证明 `---` 完全可以合法地出现在 `on:` 块结束**之后**, 且必须被当作多文档分隔): 构造文件 `name:` → `on: {push/pull_request 均带 paths}` → `jobs: {...}` → 之后一行 `---` → `some_other_top_level_key: value`。用 `PyYAML` (业界标准 YAML 语义的 ground truth, 仅用于验证语义, 非本 Spec 采用的 parser) 解析:
     ```
     number of YAML documents: 2
     --- doc 0 --- {'name': ..., True: {'push': {...}, 'pull_request': {...}}, 'jobs': {...}}
     --- doc 1 --- {'some_other_top_level_key': 'value'}
     ```
     确认这个 `---` 是合法的文档分隔符, 且它的位置在 `jobs:` 之后, 完全在 D12 声明的「`on:` 键行到 `on:` 块结束」区间**之外**。若实现者按「和 D12 用同一个扫描区间」的自然假设 (两条规则紧邻、共享上下文, 没有任何文字提示要分开处理), 这个 `---` 永远不会被看到。
  2. **SC-31(a) 自己的场景已经站在 D12 区间之外**: `:203` SC-31(a) 的场景是「**首行** `---`」——即文件第 1 行。这一行在 `name:` 之前, 更在 `on:` 键行之前, 逐字落在 D12「`on:` 键行到 `on:` 块结束」区间的**外面**。也就是说, 哪怕不构造额外反例, D13 唯一给出的两个测试场景之一 (SC-31a) 本身就要求扫描 `on:` 区间之外的内容——一个把自己的构造级判定死死限定在 `on:` 子树内的手写 parser (完全遵照 D12 的区间声明), 根本不会读到文件第 1 行, 自然也谈不上「正确忽略首行 `---`」或「错误当成分隔符」, 这一整条判定分支对它而言压根不可达。
  3. **既有 (非 A1) 基线文本进一步印证冲突**: `:57` (非 A1, R1-R4 已收敛) 明写「触发子集解析...只解析 `on:` 块的 push/pull_request 两类自动触发及其 paths: 列表」——把整个手写 parser 的职责范围限定在 `on:` 块。D13 要求的「查看首个内容行、以及其后任意位置的列 0 `---`」与这句基线陈述的范围直接矛盾, A1 未对 `:57` 做任何澄清或例外说明。

  2. `:57` 补一句例外: 「D13 (`---` 检测) 例外于本段「只解析 `on:` 块」的范围限定, 需要通读全文件」。
