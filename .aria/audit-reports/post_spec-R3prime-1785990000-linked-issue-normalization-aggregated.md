## 结论: 缺陷生成机制不在「工具不好」, 在文档结构

三轮的实测规律:

| | R1′ | R2′ | R3′ |
|---|---|---|---|
| major | ~14 | ~11 | **26** |
| fix 引入占比 | — | 10/11 | **22/26** |
| 用了什么手段 | 常规修法 | 常规修法 | **owner 缩范围裁定 + 三件专门造的工具** |

**手段越强, 缺陷越多。** 因为每一件新手段都是**新表面**, 而新表面上的缺陷密度与老表面一样。M9 是定量证据: 承诺 466→250, 实得 472。

**实测的结构比例** (按二级标题切段):

```
交付面 (What Changes / 决策记录 / Success Criteria / Impact / 非目标)   254 行  53%
审计装置与叙事 (Why / 移出范围 / 审计资产继承 / 闸门史 / 落地状态 / 头部)  219 行  46%
```

且交付面内部还嵌着大量订正留痕。**26 条 major 里, 落在纯交付面 (算法/SC/D 行本体) 的接近于零** —— 全部落在证据层、一致性层、审计叙事层。

⇒ **这份文档在同时服务两个不相容的目的**: (a) 规定要建什么; (b) 记录规定是怎么来的。目的 (b) 天然是 append-only 且自指的 (每轮都加订正留痕、计数、对前轮的交叉引用), 而正是这个 append-only 的性质在制造耦合。

**建议 (已获 owner 2026-08-07 采纳)**: **停止编辑本 Spec, 改为切开** —— 交付面抽成一份最小 Spec; 全部审计史移出为独立的 append-only 审计轨, **显式声明不维护与 Spec 的一致性**。详见随后的执行记录。

> ⚠️ **诚实提示**: 切开本身也是一次编辑, 按本轮观测的规律它同样会生成缺陷。约束方式: **机械搬运不重写** + 三件工具对结果实跑 + 切完后不再逐条修饰。
