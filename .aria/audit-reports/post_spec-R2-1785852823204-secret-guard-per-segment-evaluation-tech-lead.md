## Critical

### R2-C-1 SC-8 与 §4 的算法自相矛盾 — 按 spec 自己的伪代码写, 4 段就 +86% 破 50% 闸, 而唯一解法在转出 6

§4 的判定语义写死了求值顺序:

```
for seg in segments:
    if compute_credit(seg): continue      # 每段先算 credit
    for pat in risky_patterns: ...
```

`compute_credit` = `has_filter` 块 = **13 处 `echo "$command" | grep -qE`** (spec 自己在转出 6 承认, 我复核 = 13 ✓)。逐段化 ⇒ 这 13 个 fork 按段数线性放大。实测:

```
has_filter 块 × 1  :  29ms
has_filter 块 × 4  : 115ms   (+86ms)
has_filter 块 × 16 : 594ms   (+565ms)      ≈ 29ms/段, 严格线性

整 hook 基线 (4 段命令, 现状单次判定) 中位数 = 100.5ms
SC-8 的 50% 预算                            = 50ms
朴素逐段 4 段的增量                          = +86ms = +86%   ← 破闸
```

于是 spec 内部三方互斥:

- **SC-8** 要求 ≤50%;
- **转出 6** 明确「本版不重构 `has_filter`」;
- **§4 伪代码**规定每段先算 credit。

三者同时成立时, 3 段以上的命令必然破闸 (2 段 +29% 过, 3 段起不过) —— 而 3 段以上正是本 spec 要治的形态。Rule #10 下 Phase B 不得自行豁免 SC-8, 于是只能停摆或造假数。

**更糟的是 SC-8 根本没写测什么负载**: 「改动前后同一次会话内各跑 20 轮取中位数」—— 输入是 `echo hello` 还是 4 段命令没说。实测同一实现下这个闸的结论从 **+0%(1 段) 摆到 +86%(4 段)**。R1 M-6 要的正是「N=1/4/16 段的曲线」, 只被采纳了「改相对值」那半。

**处置方向 (二选一, 须写进 spec)**:
- (a) 把 §4 求值顺序倒过来 —— **先 pattern 后 credit** (`if seg =~ pat && ! compute_credit(seg)`), 语义完全等价 (布尔恒等), 但绝大多数段不匹配任何 pattern ⇒ `has_filter` 几乎不再逐段跑, 成本回落到基线附近。这是**范围内**的解法, 但 §4 现行伪代码不允许, 且 spec 通篇未讨论；
- (b) 承认 SC-8 依赖转出 6, 把转出 6 拉回本版或把 SC-8 降为「记录数字, 不设闸」并说明理由。

无论选哪个, **SC-8 必须写死测量负载 (段数 + 具体命令)**, 否则它测出什么全看实施者心情。

### R2-C-2 转出 2 被归类为「本 spec 明确不做」, 实为**本版发出去的 fail-close 回归** — 5/5 安全写法翻红, 无告知、无迁移指引、语料结构上抓不到

缩范围到 `;` `&&` 并没有绕开 R1 M-2 —— 因为组/循环体内部用的就是 `;`。实测 (仅切 `;` `&&`):


五条都正确丢弃了全部 stdout。分段后 `>/dev/null` 落在 `} >/dev/null` / `done >/dev/null` / `fi >/dev/null` 这种**只剩收尾记号的段**里, credit 与命令永久分离。

问题不在「本版不修」(可以接受), 在**三处定位错误**:

1. **分类错**: 转出 1-6 被统一写成「本 spec 明确不做」。但转出 1 与转出 2 是**本版新引入的行为回归** (一个 fail-open 一个 fail-close), 转出 3/4/5/6 才是「留着没做」。未来读者按标题理解为「既有缺口」, 会漏掉「上线当天用户脚本会红」这件事。

3. **测不出来**: 语料中 `expected=0` 的组/循环用例 = **0 条** (我核过全 305 条)。SC-2 只锁 15 纯管道 + 5 换行, SC-3 只管 `expected=2`。⇒ 全绿是假绿, 与 issue 自己吐槽的「347 条对两次退化全绿」同型。

**最低处置**: (1) 转出表拆两类, 标明 1/2 是本版引入; (2) Impact 行为变更 + Tasks 1.5 显式点名组/循环/条件/`( )` 四种形态并给对应迁移写法; (3) 加一条 `KNOWN-LIMIT` SC 锁住 `{ a; b; } >/dev/null` 的翻红现状 (照 SC-7 的写法), 使转出 2 收口时有红灯。

## Major

### R2-M-1 「顶层 `;` `&&` = 无歧义的命令边界」被证伪 — `[[ ]]` / `(( ))` 内它们不是命令边界, 且不在任何规则、任何 SC、任何转出项内

这是**缩范围决策的唯一论据** (§1 表依据栏、「为什么只做顶层 `;` 与 `&&`」、关键决策表都写「唯一无歧义子集」)。实测该论据不成立:

```
[[ -f /opt/.env && -s /opt/.env ]] && cat /opt/.env >/dev/null
  → 3 段: ['[[ -f /opt/.env', '-s /opt/.env ]]', 'cat /opt/.env >/dev/null']

if [[ -n $X && -f /opt/.env ]]; then echo ok; fi
  → 4 段: ['if [[ -n $X', '-f /opt/.env ]]', 'then echo ok', 'fi']

for ((i=0; i<3; i++)); do nomad var get k$i >/dev/null; done
  → 5 段: ['for ((i=0', 'i<3', 'i++))', 'do nomad var get k$i >/dev/null', 'done']
```

`[[ ]]` 里的 `&&` 是逻辑与, `(( ))` 里的 `;` 是 C 风格 for 的子句分隔 —— 都不是命令边界。切出来的 `-s /opt/.env ]]` / `i<3` / `i++))` **正是 §2 用来论证 quote-aware 必须做的那种「不完整命令片段」**: 同一条推理, 对引号做了防护, 对 `[[ ]]`/`(( ))` 一字未提。

诚实交代: 我在现有 141 条 pattern 上**没能造出行为翻转** —— 上面三条 `cur=0 post=0`, 因为没有 pattern 匹配裸 `.env` 而不带 reader 动词。所以定 Major 不定 Critical。但这恰好是 §2 自己的原话:「现在碰巧被兜住, **换一条语料就未必**」。既然这条推理足以让 quote-aware 成为硬要求, 就不能对 `[[ ]]`/`(( ))` 取相反态度。

**处置 (任选)**: (a) §1 表加一行「`[[ ]]` / `(( ))` / C-style `for` 内部不切」并进 Tasks 1.1 + SC-5; (b) 明确接受切碎, 但把「唯一无歧义子集」的措辞改成诚实的「歧义面最小的子集」, 并把 `[[ ]]`/`(( ))` 列进转出。**不接受维持现状** —— 现在既不防护、也不承认、也不转出, 三头落空。

### R2-M-3 `||` 的转出描述与 severity 失准 —— 一个字符就完整绕过本 spec 的修复; 且「需前瞻」这个理由站不住

转出 4 把 `&` / 换行 / `||` 打包成一条 **[缺陷, 中]**, 对 `||` 只写「需前瞻」。实测:

```
nomad var put p1 @f1 >/dev/null; nomad var put p2 @f2     0 → 2    ← 修好了 (= #170 泄漏形态)
nomad var put p1 @f1 >/dev/null || nomad var put p2 @f2   0 → 0    ← 一个字符, 完整逃逸
```

`a || b`(先试 A, 失败再 B) 对 `nomad var put` 是**自然的 fallback 写法**, 不是对抗性构造。本版之后, `;` 与 `||` 从「都不拦」变成「一个拦一个不拦」, 于是 `||` 成为本 spec 修复的现成绕过口。这不是「一个待做的切分记号」, 是「修复的覆盖面有个同义缺口」。

R2 任务点名的 `a && b || c` 不一致判定, 实测成立:

```
true && nomad var get k || echo x >/dev/null   → 2 段 ['true', 'nomad var get k || echo x >/dev/null'] → 0
true && nomad var get k;  echo x >/dev/null    → 3 段 ['true', 'nomad var get k', 'echo x >/dev/null'] → 2
```

`&&` 切而 `||` 不切 ⇒ `a && b || c` 里 a|b 边界可见、b|c 边界不可见, `c` 的 credit 掩护 `b`。同一条命令里两种优先级相同的记号被区别对待, 判定不自洽。

另: **「`||` 与 `|` 的区分需前瞻」这个理由本身不成立** —— 区分 `||`/`|` 与区分 `&&`/`&` 是同一次单字符前瞻, 而本版对 `&&` 已经做了 (§1 表切 `&&` 不切 `&`)。真正站得住的理由只有后半句「频次远低于 `;`/`&&`」。给错理由的代价是: 将来有人读到「需前瞻」会以为有技术障碍, 而实际障碍为零。

**处置**: `||` 从转出 4 拆出单开一条 **[缺陷, 高]**, 描述改成「`;`→`||` 的同义绕过口」并附上面两组实测; 转出 4 剩 `&`/换行 (二者都是「不切=沿用现状」, 中 级合理)。决策表 §1 的 `||` 行理由删掉「需前瞻」。

### R2-M-4 转出 1 缺可复现的工作面 —— R1 M-1 要的 pattern 枚举没进去; 第二实例漏记, SC-7 只锁了一半

转出 1 只给了 `set -o posix; set | grep foo` 一个实例, 写「需要『跨段上下文 pattern』的建模或整命令二次扫描兜底」。缺两样:

1. **工作量无从估**。R1 M-1 明确要求「枚举 `.*` / 跨段依赖的 pattern, 逐条裁定」。我复核 141 条: **1 条**无界 `.*` (就是 `set -o posix.*set|grep` 那条) + **81 条** `[^|]*` (R1 说 79, 实为 81)。这 81 条每条都可能有跨段意图, 是转出 1 真正的工作面 —— 未来接手的人只看转出 1 会以为是「改一条 pattern」。
2. **第二实例漏记, 且 SC-7 结构上锁不住它**:
   ```
   set -o posix; set | grep foo         2 → 0    ← SC-7 锁的是这条
   set -o posix && set | grep buildid   2 → 0    ← 同一 pattern 的 && 形态, 未记未锁
   ```
   SC-7 的作用是「转出 1 收口时该用例转红」。只锁 `;` 形态, 一个只处理 `;` 的兜底实现就能让 SC-7 转红并被判为收口, 而 `&&` 形态照样 fail-open。

**处置**: 转出 1 补 pattern 面数字 (1 条 `.*` + 81 条 `[^|]*` 待逐条裁定) 与 `&&` 实例; SC-7 同时锁两条。

### R2-M-5 m-3 的 enforcement 半被静默丢弃 —— ack 的命令级语义只写在散文里, 无 SC 无 task, 且语料零覆盖

§4 裁定「`# guard:ack` 维持**命令级**语义 (整条豁免), 不下沉段级」—— 决策正确。但 Tasks 1.2 只写「判定循环改逐段 (credit 逐段算) + BLOCKED 消息补段落定位」, 没有一个字要求 ack 判定留在分段之前; SC-1..SC-11 没有一条测 ack。R1 m-3 要的正是「加一条 SC 锁」。

实测下沉段级的后果 (ack 注释只落在最后一段):

```
cat /opt/.env; nomad var get x  # guard:ack: reviewed-by-owner
   命令级 (§4 裁定) = 0        段级 = 2      段: [('cat /opt/.env', 2), ('nomad var get x  # guard:ack: …', 0)]
nomad var get x; cat /opt/.env  # guard:ack: reviewed-by-owner
   命令级 = 0                  段级 = 2
```

即实施者若顺手把整个判定 (含 ack) 挪进段循环, 已被 owner 审过并 ack 的复合命令会开始被拦 —— 而语料里没有「复合命令 + ack」用例, **366 条会全绿**。这是 spec 里唯一一条「决策写了、但没有任何机制阻止实现走反」的地方。

**处置**: Tasks 1.2 写明「ack 判定必须在 `split_top_level()` 调用**之前**」; 加 SC 锁 `cat /opt/.env; nomad var get x  # guard:ack: <8+ 非空白>` 改后仍 exit=0。

## 三、缩范围后的方案自身 (R2 任务 2) — 小结

- **`;;` / `;&` / `;;&`**: 实测**无歧义风险** ✓ ——`;;` 靠「空段跳过」自然消化, fallthrough 留下的怪段不致误判。建议锁进 SC-5 (R2-m-5)。
- **`[[ ]]` / `(( ))` / C-style `for`**: **有真歧义** ✗ —— `;`/`&&` 在这里不是命令边界, 无规则无 SC 无转出 (R2-M-1)。
- **`a && b || c`**: **判定不一致** ✗ —— 实测 `||` 侧 credit 掩护 `&&` 侧命令, 且 `;`→`||` 是现成绕过口 (R2-M-3)。

即「只切 `;` 与 `&&` 就无歧义」这个断言, 三项里对一项、错两项。**方向仍然成立** (全量 305 条只翻 1 条, 干净得漂亮), 但支撑它的那句论据需要改写成诚实版本。

## 结论

缩范围是对的, 而且**有效**: R1 的 C-1、C-2 核心断言在新范围下经全量实测确实成立 (304 不变 / 1 条设计内转红 / 0 条安全回归), SC-1 与 SC-4 都真是 baseline-failing, M-4 的 12/4 论据精确无误。这版比 R1 版好得多。

不能 PASS 的原因是三处**结构性**问题, 都不是文字瑕疵:

1. **SC-8 与 §4 伪代码 + 转出 6 三方互斥** —— 按 spec 自己的算法, 4 段 +86% 必破 50% 闸, 而唯一范围内解法 (倒转求值顺序) spec 没写; 且 SC-8 连测什么负载都没定义, 结论可在 +0% 与 +86% 之间任选 (R2-C-1)。
2. **转出 2 是本版发出去的 fail-close 回归而非「不做的事」** —— 5/5 安全写法翻红, 告知面只覆盖 `a; b`, 迁移指引给错方向, 语料零覆盖使 SC-2/SC-3 全绿必为假绿 (R2-C-2)。
3. **R1 C-3 后半原样存活** —— §1 表与 Tasks 1.1 是两份行为不同的实现契约, 而 305 条语料对二者鉴别力为 0, 两种互斥实现都能全绿 (R2-C-3)。

另有两条口径/论据问题会直接误导 Phase B: 「唯一无歧义子集」被 `[[ ]]`/`(( ))` 证伪 (R2-M-1), 以及标着「口径已统一」的 68/52 实为混合口径产物、一致口径为 49 (R2-M-2) —— 后者尤其值得记: 它与 spec 头部第 6 条作者断言同型, **都是在「勘正」动作里新引入/固化的错误**, 且都不是作者自查发现的。

R1 核销 9/14 干净, 5 条半解决或静默丢弃, 且这 5 条有共同形态: **诊断被采纳进散文, 可执行的锁被丢掉**。ack (R2-M-5) 是最典型的一条 —— 决策写了、实现走反了没有任何机制会红。

verdict: **REVISE**
