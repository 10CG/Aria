### [MAJOR] `number` 侧谓词欠定, 且抽出把母 Spec 的「纯数字」漂移成更宽的「能解析为非负整数」

- **位置**: `proposal.md:56` (步骤 2) vs 母 Spec `b7c4933` §0 步骤 1 vs R2 报告 m2
- **问题**: 母 Spec 原文是「`number` 必须是**纯数字**」; 本 Spec 改成「`number_str` **必须能解析为非负整数**」。这不是同义改写 —— 它把判定从「字符形状」换成了「`int()` 能不能吃下去」, 而 Python `int()` 的接受面远宽于「纯数字」。同时 R2 点名的**空白不对称**半条**完全没被吸收**。
- **证据** (实跑 `python3`):

  ```
  ' 122'  int-> 122 | isdigit-> False
  '+7'    int-> 7   | isdigit-> False
  '1_0'   int-> 10  | isdigit-> False
  ```

  ⇒ 两个独立实现者的自然读法给出**相反结果**:
  - 实现者 A (读「非负整数」→ `try: int(s)`): `repo#1_0` **≡** `repo#10`; `repo# 122` **≡** `repo#122`; `repo#+7` **≡** `repo#7`。
  - 实现者 B (读「非负整数」→ `re.fullmatch(r'\d+', s)`, 或沿用母 Spec 的「纯数字」): 上述三对**全部不匹配** (落进不可解析分支走原串精确比较)。

  R2 报告 `post_spec-R2-…-type-design-analyzer.md:246-253` 逐字点名了两条:
  > 「空白规则只对 `left` 剥尾部, 对 `number` 侧**完全不剥** ⇒ `repo #122` 能解析、`repo# 122` **落进不可解析分支**走原串精确比较。」
  > 「『纯数字』用 `str.isdigit()` 还是 `str.isdecimal()` 还是 `int()` 亦未定」

  本 Spec 的步骤 1/3 (`:56-57`) 只剥「整串首尾空白」与「`left` 尾部空白」, **`#` 右侧的前导空白仍无人剥**; SC-6 的四个不可解析用例 (`no-hash-here` / `repo#abc` / `#5` / `10CG/#7`) **不含 `repo# 122`** —— 即 R2 逐字指出的那个分支, 抽出后仍无 SC 覆盖。
- **危害**: 本 Spec 全部内容就是这一个谓词, 它自称「钉到字符级」(`:51`)。一个多打的空格会让归一**静默退化成原串比较** ⇒ 产生本 Spec 要消灭的那种漏报, 且不可观测。
- **建议修法**: 步骤 2 改成字符级判据 + 显式空白规则, 例如「`number_str` 先剥首尾空白, 随后必须完全匹配 `^[0-9]+$` (ASCII 数字, 不接受 `+`/`-`/`_`/Unicode 数字), 再 `int()`」; SC-6 补 `repo# 122` 与 `repo#1_0` 两个用例 (前者若决定接受则移到 SC-1 正例, 关键是**钉死**而非留给实现者)。
