## 自报薄弱点

1. **track-id 断言只守文件内容, 不守提交归属**。5.9 周期 handoff 的提交没有任何一次
   `commit_attribution` 覆盖 (TASK-030 的范围在它之前), 所以「这一提交会不会被他轨判走」这件事本轮仍
   只有 owner 在第 13b 项看 diff 这一道人工关。最小修法解决的是「取值写错没人拦」, 没解决「归属判定无
   机械复核」。km 的另一种修法 (13b 之前重跑判据) 正对这一面, 本轮按派单未采。
2. **对齐通则的例外只枚举了两处**。AB 会话与 release 之后的会话写在条目里; 如果将来新增别的
   `ARIA_COORDINATION_NO_PUSH` 会话或别的不许 fetch 的窗口, 通则会与它冲突, 需要再补例外。
3. **C.2.4.5 的 PR 标签一路没有实跑**。CF-2 只实跑了 trailer 一路 (三臂); 标签一路依赖 `forgejo` CLI 与
   `ARIA_PR_NUMBER`, 在副本里没有可用的 PR, 只按代码 (`check_pr_label`) 断言其行为与失败方向。
4. **custom checks 的首行口径依赖「首行」这一形态**。若某条 check 将来把 `##SKIP##` 打到 stderr 或第二
   行, 首行判据会漏; 本轮只按现有 16 条的实际形态写死, 并在扫描清单里留了复算脚本。
5. **序号引用清单里「按上下文核过」的 38 行是人工判定**。脚本只能解析有限定词的引用; 这 38 行 (中文量
   词、同表内引用、任务自身步号等) 由我逐行读上下文判定, 判定词写在脚本的 `CONTEXT` 字典里, 复核时按该
   字典逐行对照即可, 但它本身不是机械结论。
6. **N12 的 fixture 用 `git update-ref` 把协调 ref 拨回 release 之前**, 以便同一分叉态跑两种顺序。这是
   取证手法, 不是生产路径; 两臂之间除顺序外没有其它差异, 但「同一状态两次 release」在真实执行里不会
   发生。
