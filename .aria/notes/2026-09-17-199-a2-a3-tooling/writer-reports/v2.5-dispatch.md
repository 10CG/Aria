### 3.3 两项针对性动作 (owner 点名)

**(A) 「空输出即通过」全计划同族扫描**:
- 扫描面 = 执行者会照做的判据: `tasks.md` 全文 + yaml `tasks[*].verification` + 被引为可执行检查的 metadata 键 (至少 `coord_ref_precheck` / `commit_attribution` / `coord_push_verify` / `sc12_liveness` / `standards_files_derivation` / `baseline_rebase` 相关判据)。`a2_state_runs` / `v2_state_runs` 是冻结的取证脚本, 不在扫描面, 除非某条执行判据依赖它们。
- 同族定义: 通过条件是「无输出 / 输出为空 / 零命中 / 有输出 ⇒ 停 (反面即放行)」一类, 而**命令自身失败 (退出码异常)、运行目录不对、路径或对象不存在、管道前段失败**会产生与「通过」相同的信号。已知成员: R5-M4 两处; `11c3a29f` (cr/m5: `aria_shifted` 第 6 条冒号前是三个文件名, 路径两端都不存在 ⇒ rc 0 空输出, 在新判据下读成零 diff); `ac2e8dcb` (cr/m3: `handoff_autofill.py --owner-container` 失败打印空串、退出 1, 贴入后 E1 照样得 5)。**扫描要找出全部成员, 不止这些** —— 例如嵌入脚本里 `git rev-list` / `git diff-tree` 失败时返回空列表而被当作「无领先提交」之类。
- 产出: **用脚本 (不是手数) 生成全量清单**, 每条列: 位置 / 原判据 / 失败信号与通过信号是否可区分 / 处置 (改 / 不受影响 + 理由 / 超出范围请裁)。清单贴进报告; 对「改」的每条做反事实 (旧判据在失败态放行、新判据停)。
- 改嵌入脚本 (如 `coord_ref_precheck.code`) 会影响三态证据 ⇒ 按 README 重跑两份三态脚本并归因每处输出差异。
