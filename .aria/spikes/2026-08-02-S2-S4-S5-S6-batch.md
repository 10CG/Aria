## S2 — 探针 fetch 怎么接?

### 实测数据

| 项 | 值 |
|---|---|
| 双远端 `git fetch` (origin + github) ×5 | **12.5 / 13.4 / 14.1 / 15.9 / 13.0 s** (均值 ~13.8s) |
| 单 remote: origin | ~7.0 s |
| 单 remote: github | ~7.9 s |
| 失败率 (本会话累计观测) | github 出现过 **2 次瞬时 SSH 失败** (`kex_exchange_identification`), 重试即恢复 |

### 结论

**选「自带 fetch」, 但必须修正 R3 对它的定性。**

R3/M4 建议自带 fetch 时写的是「**一个简单的、每轮跑一次 `git fetch` 到 `enforced_remotes` 的轻量实现**」。**「轻量」不成立** —— 13.8s/轮。以 R1 的 5 席 × 4 轮为例, 若每轮探针各跑一次, 净增 **~55s**; 本 Spec 自己经历的 3 轮则是 ~41s。可接受, 但不能当成零成本随手加。

**复用 `remote_refresh` 缓存判否**, 理由与 R3 一致且已实测坐实:
- 缓存 `.aria/cache/remote-refresh.json` 的**唯一写入点**是 `remote_refresh.py:691`, 而它只在 `scan.py` 的 Phase 0.5 被调用;
- ⇒ 缓存只在 `/state-scanner` 运行时刷新。audit-engine 的多轮循环**无任何机制**保证轮间跑过 state-scanner;
- ⇒ 跨天审计的后续轮次会读到首轮的陈旧缓存 = D3 要修的「首轮扫描不够」换条更深的路径复现。

### 给 Spec 的可执行结论

1. 探针**自带 fetch**, 只 fetch `enforced_remotes` 的默认分支 (不是全部 ref);
2. **配超时预算** (建议 30s, 约实测均值 2×) + 超时按 `degraded` 处置 (对齐母 Spec 的 SC-8: 不静默、exit 非 0);
3. **瞬时失败须重试** —— 本会话实测 github 两次瞬时 SSH 失败均重试即恢复 (同 CLAUDE.md 硬约束 2 对 `ls-remote` 的要求);
4. **文档不得称其「轻量」** —— 写明 ~14s/轮的实测代价, 让采用者自己判断值不值。

## S4 — basename 别名怎么处置?

### ⚠️ R2 的数字量在了错误的总体上 — ⛔ **本节结论已于 2026-08-04 作废, 见下方订正**

R2/M2 写:「R2 语料统计 `aria-orch` **24 次** vs `aria-orchestrator` **10 次**」。**实测三处都对不上**:

| 口径 | `aria-orch` (非 -orchestrator) | `aria-orchestrator` |
|---|---|---|
| `openspec/` 全文任意上下文 | **19** | **802** |
| **「关联 Issue」字段值内** (即真正会被传给 `--linked-issue` 的总体) | **0** | **0** |

⇒ (a) 比例是**反的** (19 vs 802, 不是 24 vs 10); (b) **在真实输入总体上, 别名实例数为零**。

**这条本身是个方法论实例**: R2 自己指出「三族表取自 ref 13 条而实际输入是 prose 139 篇, **两者不是同一总体**」—— 然后它在给别名举证时**犯了同一个错误, 只是下移了一层** (拿全文出现次数当输入值分布)。

### prose 语料的真实分布 (141 篇实测)

| 项 | 值 |
|---|---|
| 语料总数 | **141** 篇 (`openspec/changes/` + `archive/`) |
| 有「关联 Issue」字段 | **13 篇 = 9%** |
| 字段值形态 | org 限定 **7** / 裸形 **10** |
| 出现的真实 repo basename | **仅 2 个**: `aria-plugin` (6) / `Aria` (6) |

⇒ 真实输入总体**极小且极集中**: 13 个值, 2 个 repo。

### 结论

**不建别名表。** 依据:
- 别名在真实输入总体上**零实例**;
- 别名表本身是需要维护的新状态 (谁更新、怎么核、漂了怎么办), 对 0 实例的问题引入常驻维护成本, 性价比不成立;
- **保留 `linked-issue-normalization` 已有的处置** (D4 成文为已知限 + SC-5 断言锁定), 那已经足够 —— 它保证该限度**不会被误读成已覆盖**。

**但 S4 揭示了一个更值得做的**: 「关联 Issue」字段**只有 9% 的 proposal 有** —— 这才是主机制的真实瓶颈 (母 Spec R1/M1 已指出「省字段即免义务」)。**别名不是问题, 字段缺失才是。** ⇒ 母 Spec 重写时应把重心从「别名归一」移到「字段进模板并可校验」。

## S5 — 归一 × `derive_track_id` 碰撞域穷举

### 穷举范围与结果

真实仓名全集 (`.gitmodules` + 已知) × 代表性 issue 号 × 生产容器:

| 子项 | 组合数 | 碰撞 |
|---|---|---|
| **S5-a** §0 比较键 (5 repo × 2 org × 9 num) | 90 | **无** ✅ (org 归并是设计意图, 不计) |
| **S5-b** track-id 派生 (S3 定案形态, 5 repo × 9 num × 2 container) | 90 → 90 唯一 | **无** ✅ |

### ⚠️ S5-c/d: R3 判为 dormant 的风险**实际是活跃的**

`derive_track_id` 把 `.` / `_` / `/` 全译成 `-` (`track_id.py:71`)。R3/M3a 判定:

> 「我核查了本组织实际仓名 (`Aria`/`aria-plugin`/`aria-orchestrator`/`aria-standards`), 目前**没有含 `.`/`_` 的仓名**, 语料中暂无实例, 是**结构性 dormant 风险**」

**R3 的仓名清单不完整。实测**:

```
10cg.local vs 10cg-local → 都归一为 10cg-local-1-c  ⚠️ 碰撞
10cg.local vs 10cg_local → 都归一为 10cg-local-1-c  ⚠️ 碰撞
```

`10CG/10cg.local` 是**真实存在的仓** —— Forgejo API 实测 `full_name: 10CG/10cg.local`, **11 个 open issue**, 且本项目 handoff 里引用过它 (`10cg.local #20`, github egress 抖动)。

⇒ **不是 dormant, 是活跃**: 任何人写 `10cg.local#20` 与 `10cg-local#20` 会派生出同一个 track_id, 而 §0 的比较键判它们**不同** (§0 只做 casefold, 不译分隔符) —— **两层归一不一致**。

### 结论

1. **§0 与 `derive_track_id` 的归一必须对齐**, 或显式声明二者作用域不同并接受后果。推荐: **§0 的 `repo_basename` 归一增加同款 `./_ → -` 译码**, 使两层一致 (代价: `10cg.local` 与 `10cg-local` 在 §0 也判同一仓 —— 而它们**本来就该是同一仓的两种写法**, 这反而修好了 S4 那类别名的一个真实子集);
2. **加一条断言 SC** 钉住 `10cg.local#20` ≡ `10cg-local#20` (正例, 非已知限);
3. **修正 R3/M3a 的定性** —— 从「dormant」改「活跃, 有真实仓」。

## S6 — 要不要中心化 spec 登记表 (D5 重评)

### 三条无界缺口的真实量化

| 缺口 | 实测 |
|---|---|
| **跳 A.1 直调 `/spec-drafter`** | ✅ 真实可达 —— `spec-drafter/SKILL.md:9` `user-invocable: true` |
| **`coordination.enabled=false` opt-out** | 本仓 `enabled: true` ✅; 但该键是**每项目配置**, 第三方装机仓默认值不由本仓决定 |
| **legacy 轨** (不走 phase1_gate) | ⚠️ **实测差距显著**: coordination ref 里 **2 个**容器; 而 handoff 的 `owner-container` 出现过 **9 种** (`dev-claude` / `dev-claude2` / `simonfish/f9c6e8cd` / `simonfishgit/dev-claude` 等) ⇒ **至少 7 种身份从未在 ref 里留下 claim** |

### 结论: **仍然不做中心化登记表**, 但依据换掉

原 D5 的依据「残余缺口仅秒级」是**实质低估** (母 Spec §4 已订正)。但「不做」的结论仍成立, 新依据是:

1. **登记表解决不了这三条缺口** —— 它们的共同根因是「**没走进入口**」(跳 A.1 / 关开关 / 用旧路径)。中心化登记表同样需要有人去登记, 换个存储位置不改变「入口没被走」这个事实。**它是同一个问题的另一种载体, 不是解法。**
2. **真正能收窄缺口的是入口覆盖** —— S6 实测的 9 vs 2 说明: 提升覆盖率的杠杆在「让更多入口自动认领」(母 Spec 的 §1 双落点 phase-a-planner + spec-drafter 正是此方向), 而非新建登记表。
3. **登记表的成本是常驻的** (一致性、并发写、GC), 收益却依赖同一个前提 (有人去写)。

⇒ **D5 结论不变, 理由全部替换**。母 Spec 重写时须把 D5 的论证段整体改写, 不能沿用「秒级」那句。

### S6 附带发现 (值得单独看)

**9 种 owner-container vs 2 个 ref 容器**这个差距本身就是一个信号: 要么大量 session 没走认领, 要么 `owner-container` 的取值口径与 claim 的 container 段不一致 (回想 S3: `get_container_id()` 是 label 优先 / uuid / hostname 三分支, 而 handoff 的 `owner-container` 形如 `simonfish/bfe8285d` 是「人名/容器」复合形)。**两者口径不同已经是事实**。⇒ 母 Spec 重写时须定义这两个标识的关系, 否则「谁在做这件事」在两个系统里对不上。
